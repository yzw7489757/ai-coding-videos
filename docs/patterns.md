## P1 · Planner → Generator → Evaluator {#p1}

- **一句话**：一句话需求先由 Planner 扩写成规格，Generator 实现，独立的 Evaluator 用浏览器实测打分，不合格就打回。
- **何时用**：任务超出模型单独能稳定完成的范围，或者结果有主观标准（如设计质量）、自评容易偏宽时（[[16§3.1]]）。
- **何时别用**：任务在模型能力范围内时。作者换到 Opus 4.6 后把 Evaluator 改成只在最后跑一遍，因为它的价值取决于任务是否超出模型单独能稳定完成的边界（[[16§3.5]]）。
- **来源**：[[16§3.2]]
- **相关**：IndyDevDan 的 Builder + Validator 最小团队（[[05§3.3]]）。

## P2 · Sprint Contract {#p2}

- **一句话**：每轮开工前，写代码的代理和验收的代理先通过文件约定“这一轮做什么、怎么验证”，两边同意后再动手。
- **何时用**：规格写得很高层，从用户故事到可测试的实现之间有缺口时（[[16§3.3]]）。
- **何时别用**：作者在 Opus 4.6 上删掉了 sprint 结构，因为模型已能连续两个多小时保持连贯（[[16§3.5]]）。
- **来源**：[[16§3.3]]
- **相关**：plan mode 生成的计划里写明成功指标（[[13§3.2]]）。

## P3 · 逐个拆脚手架 {#p3}

- **一句话**：harness 的每个组件都编码了一条“模型自己做不到”的假设；模型升级后一次只删一个组件，看结果变化。
- **何时用**：换了更强的模型之后。
- **何时别用**：不要一次性大刀阔斧地删。作者第一次这样做就失败了，分不清哪些组件在承重（[[16§3.5]]）。
- **来源**：[[16§3.5]]
- **相关**：Claude Code 删掉为旧模型加的 to-do list（[[02§3.2]]）；删掉 80% 系统提示词（[[06§3.2]]）；上下文极简主义（[[01§3.7]]）。

## P4 · 锁文件认领任务 {#p4}

- **一句话**：代理在 `current_tasks/` 写一个文件“上锁”，两个代理抢同一任务时，git 同步会让后来者换一个；没有编排者。
- **何时用**：十几个代理、任务边界清楚（例如每个代理修一个不同的失败测试）时（[[17§3.2]]、[[17§3.5]]）。
- **何时别用**：代理数量很大时。Cursor 在更大规模上发现，锁会被持有太久、忘记释放，二十个代理只剩两三个的有效吞吐（[[18§3.1]]）。
- **来源**：[[17§3.2]]
- **相关**：站内暂无同类实践。

## P5 · Oracle 驱动的并行修 bug {#p5}

- **一句话**：用一个已知正确的系统（如 GCC）编译大部分文件，只让被测系统编译一小部分，把一个大故障拆成多个可以并行修的小故障。
- **何时用**：所有代理都撞上同一个大 bug、互相覆盖修改时（[[17§3.5]]）。
- **何时别用**：没有可信的参照系统时，这个方法用不上。
- **来源**：[[17§3.5]]
- **相关**：站内暂无同类实践。

## P6 · Planner / Worker / Judge {#p6}

- **一句话**：分层协作：Planner 持续拆任务（可派生子 Planner），Worker 只做自己的任务、不管协调，Judge 在每轮结束时决定是否继续。
- **何时用**：几百个代理、需要持续拆分任务的长期项目（[[18§3.2]]）。
- **何时别用**：别加多余的层。Cursor 的 integrator 角色制造的瓶颈比解决的还多；结构太多，系统会变脆弱（[[18§3.4]]）。
- **来源**：[[18§3.2]]、[[38§3.4]]
- **相关（对照）**：Grok Build 的扁平并行子代理 + skeptic 验证（[[15§3.2]]）。续篇的最终版去掉了 Judge，改由 Worker 交接报告驱动 Planner 持续规划（[[38§3.4]]）。

## P7 · Ralph 循环 {#p7}

- **一句话**：外层 `while` 循环 + 每轮全新上下文 + 一轮只做一个目标 + 每轮开头固定放入规格和计划。
- **何时用**：规格清晰、能自动验证的任务（[[24§4]]）。
- **何时别用**：规格有错时，循环会高效地放大错误；也不要在没有隔离的机器上放开权限跑（[[24§4]]、[[24§3.1]]）。
- **来源**：[[24§3.2]]、[[24§3.3]]、[[24§3.4]]；同类做法 [[17§3.1]]
- **相关（对照）**：Codex `/goal` 在 harness 内部循环，靠可验证目标结束（[[09§3.6]]）。

## P8 · 规则文件“少即是多” + 指针 {#p8}

- **一句话**：CLAUDE.md / AGENTS.md 只写每次都用得上的 WHAT / WHY / HOW，细节拆到 `agent_docs/`，根文件里只放目录和一句话简介。
- **何时用**：规则文件越来越长、代理开始无视其中指令时（[[20§3.3]]、[[20§3.4]]）。
- **何时别用**：这个模式控制的是总量，不反对“犯错就补一条规则”；补的那条要普遍适用（[[20§4]]）。
- **来源**：[[20§3.4]]、[[20§3.5]]
- **相关**：AGENTS.md 宁短勿乱，消除互相矛盾的指令（[[10§4]]、[[10§5]]）；上下文极简主义（[[01§3.7]]）。

## P9 · 风格交给工具 {#p9}

- **一句话**：别让 LLM 干 linter 的活；在意格式就用 Stop hook 跑 formatter / linter，把错误交回给代理修。
- **何时用**：规则文件里塞了大量代码风格条目时（[[20§3.6]]）。
- **何时别用**：#20 本身没有给出 hook 配置原文；可照抄的官方配置见 [[28§3.2]]（改完自动格式化）和 [[28§3.3]]（拦住对敏感文件的修改）。如果代理也会通过 Bash 改文件，只匹配 `Edit|Write` 会漏掉（[[28§3.2]]）。
- **来源**：[[20§3.6]]
- **相关**：先让代理自由探索，在 lint / test 阶段再施加约束（[[07§3.3]]）；Hooks 确定性闸门（[P21](#p21)）。

## P10 · Skills 渐进加载 {#p10}

- **一句话**：skill 的元数据常驻上下文，需要时才读 SKILL.md，再按需读附属文档或运行脚本。
- **何时用**：有大量只对特定任务有用的说明，不想让它们每次都占上下文时（[[21§3.3]]）。
- **何时别用**：每次都需要的项目信息，仍然应该放在规则文件里（[[20§3.1]]）。
- **来源**：[[21§3.3]]
- **相关**：复用已有 skills 作为设计上下文（[[14§3.1]]）；Codex 把 skills 列表上限设为上下文窗口的 2%（[[09§3.2]]）。

## P11 · 密钥与写权限分离的 CI 代理 {#p11}

- **一句话**：只读 job 拿 API key 生成补丁 → 上传 artifact → 无密钥、有写权限的 job 开 PR。
- **何时用**：任何让代理在 CI 里改代码的场景（[[22§3.2]]、[[22§3.3]]）。
- **何时别用**：不要把 API key 设成整个 job 的环境变量、同时给写权限；构建脚本、测试、依赖钩子都能读到它（[[22§3.2]]）。
- **来源**：[[22§3.3]]
- **相关**：OpenAI 让 100% 的 PR 都过 Codex 审查（[[10§3.3]]）。这一节讲的是 CI 里的审查流程，不涉及密钥布局。

## P12 · Issue 扇出 + 每个 issue 一个 worktree {#p12}

- **一句话**：先把工作拆成 GitHub issue，每个 issue 一个 worktree，并行实现，各自开 PR。
- **何时用**：一批互不依赖、已经划好范围的 bug 和功能（[[23§3.1]]、[[23§3.2]]）。
- **何时别用**：还没有自动验证时。没有能自动判断 PR 是否基本可用的验证，就不可能同时并行多个代理（[[26§3.4]]）。
- **来源**：[[23§3.1]]、[[23§3.2]]
- **相关**：worktrees 是 Codex 并行的基础（[[08§3.1]]）；Peter 用多份 checkout 代替 worktree（[[11§3.2]]）；扇出 + 对抗式复核（[[02§3.5]]）。

## P13 · 全新上下文审查 + 跨模型审查 {#p13}

- **一句话**：写代码的会话不审自己的代码：先 `/clear`，再用审查命令派子代理审；再让另一家的模型挑一遍。
- **何时用**：代理开出 PR 之后、人审之前（[[23§3.3]]）。
- **何时别用**：它不能代替人审，Cole 强调代理审查之后合并前人仍然要自己审（[[23§4]]）。
- **来源**：[[23§3.3]]；独立 Evaluator 的同类思路见 [[16§3.4]]
- **相关**：扇出 + 对抗式复核（[[02§3.5]]）；只读审查 persona（[[08§3.5]]）；Codex Auto Review 用只读子代理审批越权操作（[[09§3.4]]）；skeptic 证伪（[[15§3.3]]）。

## P14 · 自愈层：每个错误都改环境 {#p14}

- **一句话**：修 bug 的同时，修那个允许 bug 出现的规则、技能或流程。
- **何时用**：同一类错误反复出现时（[[23§3.4]]、[[27§3.5]]）。
- **何时别用**：新增内容要控制总量，特定任务的经验应放进 `agent_docs/` 或 skill（[[20§4]]）。
- **来源**：[[23§3.4]]、[[27§3.5]]
- **相关**：每次犯错写进 CLAUDE.md 或 Skill（[[01§3.1]]）；Garbage Collection Day + persona reviewer（[[07§3.6]]）。

## P15 · Red / Green TDD 提示词 {#p15}

- **一句话**：一句 “Use red/green TDD” 就能让代理先写测试、确认失败，再实现到通过。
- **何时用**：担心代理写出不能运行或用不上的代码时（[[25§3.1]]）。
- **何时别用**：关键是先看到测试失败；跳过这一步，可能写出本来就能通过的测试（[[25§3.1]]）。
- **来源**：[[25§3.1]]
- **相关**：站内暂无同类实践。

## P16 · First run the tests {#p16}

- **一句话**：在已有项目里开新会话，第一句话先让代理跑测试。
- **何时用**：项目已有测试集时（[[25§3.2]]）。
- **何时别用**：测试输出太长会占满上下文，只输出失败用例（[[24§3.6]]、[[17§3.4]]）。
- **来源**：[[25§3.2]]
- **相关**：让代理用你已有的工具验证自己（[[10§3.2]]）。

## P17 · 代理手动测试 + 留证据 {#p17}

- **一句话**：测试通过后，再让代理用 `python -c`、curl、浏览器亲手跑一遍，并用 Showboat 记录过程。
- **何时用**：测试全绿但服务可能一启动就崩、关键按钮没显示时（[[25§3.3]]）。
- **何时别用**：记录不能代替你自己确认，交给同事前仍要自己审（[[25§3.5]]）。
- **来源**：[[25§3.3]]、[[25§3.4]]
- **相关**：无头浏览器自测（[[13§3.4]]）；用 Claude Tag 开发 Claude Tag 的验证闭环（[[02§3.6]]）。

## P18 · 8 根验证支柱打分 {#p18}

- **一句话**：按 8 个维度给代码库的可验证性打分，补最弱的一项。
- **何时用**：想并行多个代理或做大规模迁移之前（[[26§3.2]]、[[26§3.4]]）。
- **何时别用**：来源没有讨论不适用的场景。
- **来源**：[[26§3.2]]
- **相关**：just-in-time lint / test 约束（[[07§3.3]]）；让代理用已有工具验证自己（[[10§3.2]]）。

## P19 · 能力评测“毕业”进回归集 {#p19}

- **一句话**：能力评测起始通过率偏低；题目稳定通过后，移进回归套件，在 CI 里持续跑。
- **何时用**：在系统地评测一个代理或 prompt 时（[[19§3.4]]）。
- **何时别用**：来源没有讨论不适用的场景；评测只是多层防护中的一层（[[19§3.7]]）。
- **来源**：[[19§3.4]]
- **相关**：站内暂无同类实践。

## P20 · 下班前 30 分钟启动代理 {#p20}

- **一句话**：利用人本来就不工作的时间，让代理做深度调研、并行试探模糊想法、做 issue / PR 分诊。
- **何时用**：第二天需要一个“热启动”时（[[27§3.3]]）。
- **何时别用**：分诊时不允许代理直接回复，只要第二天的报告（[[27§3.3]]）。
- **来源**：[[27§3.3]]
- **相关**：Routines 把代理挂到事件流上（[[01§3.3]]）；从本地到云端的 Loops 与 Routines（[[02§3.4]]）。

## P21 · Hooks 确定性闸门 {#p21}

- **一句话**：能用脚本判断的规则（格式化、禁止改敏感文件），写成在固定时刻一定会执行的 hook；`PreToolUse` 用退出码 2 拦截并把理由交给代理。
- **何时用**：某条规则必须每次都执行、不能依赖模型自觉时（[[28§2]]、[[28§3.3]]）。
- **何时别用**：每次会话都要知道的背景应该写进规则文件，而不是 hook（[[28§3.4]]）；`PostToolUse` 不能撤销已发生的动作（[[28§4]]）。hook 自己出错时默认放行，关键安全检查不能只靠它（[[34§3.2]]）。
- **来源**：[[28§3.2]]、[[28§3.3]]、[[28§3.5]]
- **相关**：风格交给工具（[P9](#p9)）；Gemini CLI 和 Grok Build 的同类配置（[[28§3.6]]、[[34§3.2]]）；官方 Ralph 插件用 Stop hook 续跑（[[24§3.4]]）。

## P22 · 计划存进仓库，代理按清单打勾 {#p22}

- **一句话**：每个功能生成 `spec.md` 和 `plan.md` 放进仓库，人审过计划再执行，代理每完成一项就打勾，状态在文件里，随时可以中断和恢复。
- **何时用**：比改一两行代码更复杂、可能跨多个会话或多人协作的任务（[[29§3.2]]、[[29§3.3]]）。
- **何时别用**：小改动不值得开一套流程；而且读写这些文件会增加 token 消耗（[[29§4]]）。
- **来源**：[[29§3.2]]、[[29§3.3]]
- **相关**：RPI 分阶段写文档交接（[[04§3.4]]）；plan mode 批准后才开工（[[13§3.2]]）。

## P23 · 迁移分支 + 临时脚手架 {#p23}

- **一句话**：大迁移开一条专用分支并写好背景说明，先搭一层让新旧实现并存的脚手架，代理逐块迁移并通过 PR 合回迁移分支，全部完成后拆掉脚手架再合入 main。
- **何时用**：互相依赖、无法一次做完、又希望每一步都能测试的大迁移（[[30§3.2]]、[[30§3.4]]）。
- **何时别用**：改动彼此独立时，逐个处理就够了，不需要脚手架（[[30§3.4]]）。讲者也说脚手架代码“很丑”，只是过渡。
- **来源**：[[30§3.2]]、[[30§3.4]]
- **相关**：每个 issue 一个 worktree（[P12](#p12)）。

## P24 · 按依赖图分批：验证器 + 修复器 {#p24}

- **一句话**：把代码库按依赖图分成 PR 大小的批次，从叶子节点开始，先跑验证器（测试、linter 或按规则检查的模型），不通过的批次交给修复器代理开 PR，人审合并后再往上做。
- **何时用**：几百个文件的代码清理、类型补全、依赖升级（[[30§3.3]]）。
- **何时别用**：来源是 OpenHands 的内部工具演示，没有对照实验；同时运行的代理数刚开始建议控制在 3–5 个（[[30§3.2]]、[[30§4]]）。
- **来源**：[[30§3.3]]
- **相关**：用 GCC 当 Oracle 拆出可并行的小任务（[P5](#p5)）。

## P25 · 精确率优先的 AI 审查器 {#p25}

- **一句话**：审查意见只在“发现真问题的收益”大于“核实成本 + 误报代价”时才发；给审查者整个仓库和执行能力，用 AGENTS.md 调整松紧。
- **何时用**：AI 审查意见太多、开发者开始忽略它时（[[31§3.1]]）。
- **何时别用**：代理式审查器如果反而太谨慎，需要往“多报”方向纠偏（[[33§3.5]]）。也不要把一次干净的审查当成安全保证（[[31§4]]）。
- **来源**：[[31§3.1]]、[[31§3.2]]
- **相关**：OpenAI 团队的 PR 审查有意做得“不吵”（[[10§3.3]]）。

## P26 · 多次审查投票 + 用解决率迭代 {#p26}

- **一句话**：同一个 diff 用不同顺序并行审查多次，只保留被多次发现的问题；再用“合并时被修掉的比例”衡量审查机器人，每次改动都用这个指标检验。
- **何时用**：要降低误报，或者想知道审查机器人到底有没有用时（[[33§3.1]]、[[33§3.3]]）。
- **何时别用**：解决率衡量的是作者有没有改，不等于问题真实存在；Cursor 的数据和 BugBench 都没有公开（[[33§4]]）。
- **来源**：[[33§3.1]]、[[33§3.3]]、[[33§3.4]]
- **相关**：代理结果有随机性，要用多次作答的统计描述（[[19§3.5]]）。

## P27 · 测试计划基于源码，操作前先写预期 {#p27}

- **一句话**：让代理实测改动前，先读相关代码写测试计划；每一步操作前写下预期结果；重复的准备步骤（如登录）写成确定性脚本；最后交回截图和断言清单。
- **何时用**：代理用浏览器或 Computer Use 测试 UI 改动时（[[32§3.1]]、[[32§3.2]]）。
- **何时别用**：能用单元测试或状态检查验证的，优先用确定性测试（[[19§3.2]]）。Computer Use 还有截图时机和“用 JavaScript 走捷径”的问题（[[32§4]]）。
- **来源**：[[32§3.1]]、[[32§3.2]]、[[32§3.3]]
- **相关**：Red / Green TDD（[P15](#p15)）；代理手动测试 + 留证据（[P17](#p17)）。

## P28 · 按专长设计子代理 {#p28}

- **一句话**：子代理的作用是给主代理省上下文；按专长分工，比如搜索用快模型 + 只读工具，难题交给推理模型，外部库查询和批量重构各一个。
- **何时用**：主代理经常因为搜索耗尽上下文，或者因为读得太少陷入反复重试时（[[35§3.3]]、[[35§3.4]]）。
- **何时别用**：来源是产品演讲，子代理的模型配置是 2025 年底的状态；Amp 后来也认为模型变强后 harness 的影响在减小（[[35§4]]）。
- **来源**：[[35§3.3]]、[[35§3.4]]
- **相关**：子代理用来控制上下文，而不是扮演角色（[[04§3.3]]）；把审查切片交给子代理（[[08§3.4]]）。

## P29 · 用代码调用 MCP，工具按需加载 {#p29}

- **一句话**：把 MCP 服务器包装成文件系统里的代码 API，代理只读取需要的工具文件；大数据在执行环境里过滤后，只把摘要交给模型。
- **何时用**：接了很多 MCP 工具、工具定义或中间结果撑爆上下文时（[[36§3.1]]、[[36§3.2]]）。
- **何时别用**：需要安全的代码执行沙箱、资源限制和监控，工具少、数据小时直接调用更简单（[[36§4]]）。
- **来源**：[[36§3.3]]、[[36§3.4]]
- **相关**：Skills 渐进加载（[P10](#p10)）；Codex 延后加载工具（[[09§3.2]]）；对照：Amp 选择少接 MCP（[[35§3.2]]）。

## P30 · 统一开发入口 + 进程交给 supervisor {#p30}

- **一句话**：把杂乱的构建命令、参数和工具脚本收进一个 CLI，每个子命令带 `--help`；长时间运行的构建和服务由 supervisor 监控重启，不让模型去盯进程。
- **何时用**：代理会读代码、却总是跑不起项目，或者写了 skills 仍然频繁踩坑时（[[37§3.2]]）。
- **何时别用**：项目一两条命令就能跑起来时没必要。Cursor 的 `anydev` 是内部工具，文中没有代码或命令示例，需要自己实现（[[37§4]]）。
- **来源**：[[37§3.2]]
- **相关**：Skills 渐进加载（[P10](#p10)）；8 根验证支柱打分（[P18](#p18)）；自愈层（[P14](#p14)），Cloud Doctor 读 trace 修 skill（[[37§3.5]]）。

## P31 · 递归 Planner + 交接报告，接受小错误率 {#p31}

- **一句话**：Planner 只拆任务不写代码，范围大就派生子 Planner；Worker 在自己的副本上做完，写一份含发现、担忧和偏差的交接报告交回；中间提交不要求 100% 正确，最后留一轮整合修复。
- **何时用**：几百个代理长时间跑同一个大项目、全局同步代价太高时（[[38§3.4]]、[[38§3.5]]）。
- **何时别用**：代理少、任务边界清楚时，锁文件或扁平结构就够（[P4](#p4)）。原文的最终整合修复环节只是推论，没有给出实现（[[38§4]]）。
- **来源**：[[38§3.4]]、[[38§3.5]]
- **相关**：Planner / Worker / Judge（[P6](#p6)）；对照：验证器要近乎完美（[[17§3.3]]）。

## P32 · 风险分类器代替审批弹窗 {#p32}

- **一句话**：工具调用执行前，由一个小模型分类器结合用户请求判断风险；低风险放行，高风险拦截并把理由还给主代理，让它换更安全的做法，只有少数情况才打断用户。
- **何时用**：审批弹窗太多、用户开始不看就点同意时（[[39§2]]、[[39§3.3]]）。
- **何时别用**：分类器是降低风险的手段，不是安全保证；Cursor 没有公开准确率和漏拦率（[[39§4]]）。能用白名单或沙箱确定性处理的动作，先交给它们（[[39§3.5]]）。
- **来源**：[[39§3.2]]、[[39§3.3]]
- **相关**：Codex Auto Review 只读审批子代理（[[09§3.4]]）；Hooks 确定性闸门（[P21](#p21)）。

## P33 · 判断器评测：真实会话 + 合成用例 + 重复跑找翻转 {#p33}

- **一句话**：给 LLM 判断器（分类、审查、评分）建评测集时，用真实使用数据代表日常情况，用合成用例补罕见的最坏情况；评测跑在生产同一条链路上；同一用例重复跑，结果不一致的说明策略没写清楚。
- **何时用**：你的产品或流程里有一个 LLM 在做放行 / 拦截、通过 / 不通过的判断时（[[39§3.4]]）。
- **何时别用**：能写成确定性检查的就别用 LLM 判断（[[19§3.2]]）。策略一变就要重标评测集，维护成本不低（[[39§3.4]]）。
- **来源**：[[39§3.4]]
- **相关**：能力评测“毕业”进回归集（[P19](#p19)）；pass@k / pass^k（[[19§3.5]]）。

## P34 · 长时代理放进持久化执行，workflow 要短 {#p34}

- **一句话**：代理循环放进 Temporal 这类持久化执行框架，扛住机器和推理服务故障；一个任务一个短 workflow，做完就退出；代理循环、机器状态和对话状态分开管理。
- **何时用**：云端代理要跑几小时到几周、经常遇到 pod 替换或 API 故障时（[[40§3.2]]、[[40§3.3]]）。
- **何时别用**：本地单次会话用不上；这是平台级投入，文中没有 workflow 代码（[[40§4]]）。
- **来源**：[[40§3.2]]、[[40§3.3]]
- **相关**：Ralph 外层循环（[P7](#p7)）；进度落在文件里（[[17§3.4]]）。

## P35 · 定时代理：书签读取 + 确认后记账 {#p35}

- **一句话**：每个数据源记一个书签，从上次位置读；某个源读失败时书签不动、输出里写明；对外发消息前先查是否已发，对方确认成功后才更新书签和账本，不确定就标记“可能已发”、什么都不改。
- **何时用**：任何按时间表无人值守运行、会读外部数据并产生副作用的代理任务（[[41§3.3]]、[[41§3.5]]）。
- **何时别用**：一次性、有人在场的任务不需要这么重的状态管理。参考实现绑定 Claude Managed Agents beta，配置格式可能变化（[[41§4]]）。
- **来源**：[[41§3.3]]、[[41§3.4]]、[[41§3.5]]
- **相关**：密钥与写权限分离的 CI 代理（[P11](#p11)）；长时代理放进持久化执行（[P34](#p34)）。

## P36 · 推理和编辑分给两个模型 {#p36}

- **一句话**：Architect 模型只负责用自然语言描述怎么解决，Editor 模型只负责把方案变成格式正确的代码编辑；两个角色可以用不同模型，也可以是同一个模型分两步。
- **何时用**：强推理模型经常输出格式错误的补丁，或者想用贵模型想、便宜模型写时（[[44§3.1]]、[[44§3.2]]）。
- **何时别用**：对延迟敏感的交互场景要掂量两次推理的成本；数据来自 2024 年的模型和单一基准，今天的提升幅度未必一样（[[44§4]]）。
- **来源**：[[44§3.2]]、[[44§4]]
- **相关**：对照：Amp 把推理模型做成按需调用的子代理（[[35§3.4]]）；按专长设计子代理（[P28](#p28)）。

## P37 · 大脑和双手解耦：日志在外、凭据不进沙箱 {#p37}

- **一句话**：把代理拆成 session（只追加的事件日志）、harness（无状态循环）和 sandbox（可丢弃的执行环境）；harness 崩溃从日志恢复，容器挂了当作工具报错重建；凭据放在沙箱外，经 git remote 或代理服务注入。
- **何时用**：自己搭托管代理或云端代理平台、需要长时间可靠运行和多环境接入时（[[45§3.2]]、[[45§3.3]]）。
- **何时别用**：本地单机用代理时用不上；原文只给出接口概念，没有代码和成本数据（[[45§4]]）。
- **来源**：[[45§3.2]]、[[45§3.3]]、[[45§3.4]]
- **相关**：长时代理放进持久化执行（[P34](#p34)）；Cursor 的循环、机器、对话状态解耦（[[40§3.3]]）。

## P38 · 代理记忆：只记约定、决定和事实 {#p38}

- **一句话**：让代理在会话之间保留笔记时，只记团队约定、决定及理由、项目的持久事实；不记任务状态、未定结论、密钥和仓库文档里已有的；笔记按主题整理，人能浏览和修改，当前指令优先。
- **何时用**：同样的项目知识每次都要重新告诉代理，或者规则文件越写越长时（[[46§3.2]]、[[46§3.3]]）。
- **何时别用**：自动写入的笔记可能记错，要定期检查；原文没有效果数据，也没说明团队怎么共享（[[46§4]]）。
- **来源**：[[46§3.2]]、[[46§3.3]]、[[46§3.4]]
- **相关**：规则文件“少即是多” + 指针（[P8](#p8)）；自愈层（[P14](#p14)）。

## P39 · Skill 评测：小测试集 + 反例 + 确定性检查先行 {#p39}

- **一句话**：把 Skill 当提示词评测：先写可检查的“完成的定义”，用 10–20 条 prompt（至少一条不该触发的反例）跑代理，先从结构化事件流里查命令和文件，主观风格再让模型按固定 JSON 格式打分；每次手动修正都变成一行新用例。
- **何时用**：改了 Skill 或提示词，不确定是变好还是只是变了；Skill 有时不触发、误触发或漏步骤（[[47§3.3]]、[[47§3.4]]）。
- **何时别用**：结果很难用命令检查的 Skill（写作、判断类），原文没覆盖；模型评分的偏差原文没讨论，要和人工抽查对照（[[47§4]]）。
- **来源**：[[47§3.1]]、[[47§3.4]]、[[47§3.5]]、[[47§3.6]]
- **相关**：能力评测“毕业”进回归集（[P19](#p19)）；评测的零件和评分器选择见 [[19§3.2]]。

## P40 · 评测的资源配置当实验变量 {#p40}

- **一句话**：代理评测的分数受 CPU、内存、超时、时段影响；记录并固定这些配置，分开写“保证分配”和“硬上限”，多次运行；配置未对齐时，小于 3 个百分点的差距不下结论。
- **何时用**：比较模型、比较两版 prompt 或 Skill、看排行榜选模型时（[[50§3.6]]、[[50§4]]）。
- **何时别用**：静态基准（只给输出打分、不运行环境）受影响小；SWE-bench 这类不吃资源的任务效应也小得多（[[50§3.4]]）。
- **来源**：[[50§3.1]]、[[50§3.3]]、[[50§3.6]]
- **相关**：pass@k 描述随机性（[[19§3.5]]）；评测跑在和生产相同的循环里（[[39§3.4]]）。

## P41 · 一个任务一台云端机器，prompt 里写证明方法 {#p41}

- **一句话**：每个任务开一个独立的云端会话（新 VM、新分支），prompt 写成“哪里错 / 什么算完成 / 用哪条命令证明”的自包含工单；云端 CPU 不是你的，可以要求反复验证（比如测试连跑 30 次）。
- **何时用**：几个互不相关的小修复、需要长时间反复验证的问题、要跑不可信代码时（[[48§3.4]]）。
- **何时别用**：任务需要本机才有的数据库、VPN、GPU 或硬件，或要几秒一次的视觉迭代（[[48§3.3]]）；并行会话彼此看不见，同一文件的任务别并行（[[48§3.1]]）。
- **来源**：[[48§3.1]]、[[48§3.4]]、[[48§3.6]]
- **相关**：Issue 扇出 + 每个 issue 一个 worktree（[P12](#p12)）；下班前 30 分钟启动代理（[P20](#p20)）。

## P42 · 执行下放，推理留在云端 {#p42}

- **一句话**：云端代理的循环和推理留在厂商侧，执行环境放进自己的网络；执行节点主动开出站长连接接收工具调用，按排队请求扩容，空闲时休眠快照而不是删除。
- **何时用**：代理要访问内网服务、源代码管理，或需要 GPU、Mac、难以打包的构建流程时（[[51§2]]）。
- **何时别用**：不能接受代码片段随工具输出离开网络时（[[51§3.4]]）；没有平台团队维护 spawn 脚本和 pool 时，先用厂商托管环境。
- **来源**：[[51§3.1]]、[[51§3.2]]、[[51§3.4]]
- **相关**：大脑和双手解耦（[P37](#p37)，对照：#45 是厂商内部架构，#51 是把“双手”交给客户）。

## P43 · Skill 的 description 写成路由合约，AGENTS.md 规定何时必须用 {#p43}

- **一句话**：description 写清“什么时候用、什么改动触发、是否必须”；AGENTS.md 最上面用 if/then 规则指定哪些改动必须调用哪个 Skill；重复的 shell 步骤写进 Skill 的 `scripts/`，判断留给模型。
- **何时用**：仓库里有反复出现的维护流程（改完跑全套检查、写 PR 说明、发版检查），或代理时而用、时而不用某个 Skill 时（[[55§3.2]]、[[55§3.3]]）。
- **何时别用**：一次性任务不值得写 Skill；原文的吞吐增长同时受 Codex 自动审查影响，不能把效果全算在 Skill 上（[[55§4]]）。
- **来源**：[[55§3.1]]、[[55§3.2]]、[[55§3.3]]
- **相关**：Skills 渐进加载（[P10](#p10)）；Skill 评测（[P39](#p39)），可以用来检查 description 改完后触发是否更准。

## P44 · 评审默认放行，阻止必附证据和解锁清单 {#p44}

- **一句话**：让代理做发版或兼容性评审时，从“可以发布”出发，只有 diff 里有具体证据才判阻止；每个阻止都要附带具体的解锁清单。
- **何时用**：发版前的兼容性检查、迁移说明检查这类“要一个能行动的结论”的评审（[[55§3.4]]）。
- **何时别用**：高风险变更不能只靠默认放行；需要在多个可行方案中做选择的改动，仍要人审（[[55§3.5]]）。
- **来源**：[[55§3.4]]
- **相关**：精确率优先的 AI 审查器（[P25](#p25)）。

## P45 · 稳定前缀 + 易变内容放到缓存断点之后 {#p45}

- **一句话**：系统提示和工具定义只放很少变化的内容，并尽量删短；低频工具按需加载；缓存断点放在稳定层之后、对话之前；环境信息、skills 这类随请求变化的内容挪到断点之后。
- **何时用**：自己拼请求或写 harness、长任务 token 成本高、规则文件越写越长时（[[54§3.1]]、[[54§3.3]]）。
- **何时别用**：显式缓存断点依赖服务商支持；高频工具和会被“幻觉调用”的工具不要下放（[[54§3.2]]）。删规则要用真实流量 A/B 验证，不只看 evals（[[54§3.1]]）。
- **来源**：[[54§3.1]]、[[54§3.2]]、[[54§3.3]]
- **相关**：用代码调用 MCP，工具按需加载（[P29](#p29)）。

## P46 · 两段式动作分类器 + 拒绝后继续 {#p46}

- **一句话**：只读工具和项目内改动直接放行；其余动作先过一个宁可错拦的单 token 过滤，被拦的再推理复核；分类器只看用户消息和工具调用；拒绝作为工具结果交还代理，连续 3 次或累计 20 次才停下找人。
- **何时用**：想摆脱逐条审批、又不想用全放开模式的长任务（[[56§3.2]]、[[56§3.5]]）。
- **何时别用**：高风险的生产或共享基础设施操作：完整流程对真实“过度主动”动作仍漏 17%，不能替代认真的人工审查（[[56§4]]）。
- **来源**：[[56§3.2]]、[[56§3.4]]、[[56§3.5]]
- **相关**：风险分类器代替审批弹窗（[P32](#p32)，对照：Cursor 的分类器能读文件和 Grep，Anthropic 的分类器刻意不看工具输出，见 [[39§3.2]]）。

## P47 · 把开放任务改写成“合约 + 一致性测试”再交给代理 {#p47}

- **一句话**：不说“给这个平台加支持”，而是先定义接口、写好黑盒一致性测试，把任务改写成“实现这份合约、通过这些测试”；必选能力和可选能力分档，不支持的请求在改状态之前就拒绝。
- **何时用**：要接入多个相似的后端或平台、希望代理能独立写出每一个适配层时（[[53§3.5]]）。
- **何时别用**：原文的六周和两天是厂商自述，首版 driver 之后仍有大量加固工作；接口还没稳定时先别急着让代理批量实现（[[53§4]]）。
- **来源**：[[53§3.3]]、[[53§3.5]]
- **相关**：把团队规范变成 lint 和测试（[[07§3.2]]）；按依赖图分批：验证器 + 修复器（[P24](#p24)）。

## P48 · 代理配置的回归评测：旧代码 + 新配置 + 越界即失败 {#p48}

- **一句话**：从合并过的 PR 里取 20–50 个真实任务写成 eval（起点 commit、prompt、允许改的目录、可执行检查）；CLAUDE.md、skills、hooks 一改就在 CI 里用旧代码套新配置重做，评测文件先拷走，检查前后都查越界改动，通过率不够就挡住合并；每次事故补一条。
- **何时用**：团队共用一份 CLAUDE.md / skills / hooks，经常有人改，且已经有能非交互运行代理的 CI（[[57§3.1]]、[[57§3.3]]）。
- **何时别用**：预算紧时别每个 PR 都跑全套，原文也提到可以按固定节奏离线跑；每条只跑一次，偶发失败会误挡合并，要自己定阈值或重跑规则（[[57§4]]）。
- **来源**：[[57§3.2]]、[[57§3.3]]、[[57§3.4]]
- **相关**：能力评测“毕业”进回归集（[P19](#p19)）；Skill 评测：小测试集 + 反例 + 确定性检查先行（[P39](#p39)）。

## P49 · 实现前由独立角色建完成标准，实现者看不到用例 {#p49}

- **一句话**：大任务开工前，让一个不参与实现的验证者从需求和参考系统推出加权的可执行检查；标准只能加强不能塌缩；验证者测候选、按根因聚类，只把功能级的缺口告诉实现者，由第三方决定何时交付。
- **何时用**：有参考系统或可验证规格的大任务（重写、迁移、复刻），代理容易“局部全绿、整体缺一大块”时（[[59§3.2]]、[[59§3.6]]）。
- **何时别用**：小改动；或预算紧时：gdal 一格系统花了单代理 14 倍额度、13 倍时间，每格只跑一次，部分任务反而下降（[[59§3.5]]、[[59§4]]）。
- **来源**：[[59§3.3]]、[[59§3.4]]
- **相关**：Planner → Generator → Evaluator（[P1](#p1)，对照：Evaluator 直接把具体问题反馈给 Generator，见 [[16§3.4]]）；Builder + Validator 最小团队（[[05§3.3]]）。

## P50 · 审查强度随结果递减，同一错误两次就变 lint 规则 {#p50}

- **一句话**：交给代理的迁移或持续维护，先和它定一个安全做法，早期每个 PR 细审；修复站得住以后逐步少审；代理看到同一个错误出现两次，就把它固化成一条 lint 规则。
- **何时用**：几百个 PR 的迁移、设计系统维护这类“容易开始、难以收尾”或永远做不完的工作（[[58§3.3]]）。
- **何时别用**：原文没有给出“什么时候可以少审”的判断标准，也没有失败案例；出错代价高的改动别按 PR 数量放松审查（[[58§4]]）。
- **来源**：[[58§3.3]]
- **相关**：把反复漏过 review 的问题编码进规则（[[10§3.4]]）；把团队规范变成 lint 和测试（[[07§3.2]]）。

## P51 · 审查分层，人工批准按改动风险定档 {#p51}

- **一句话**：把审查拆成多层（提交前自证 → AI 审查 → 安全审查 → CI → 按风险的人工批准 → merge queue / flag / 分阶段发布 → 快速回滚）；分类器按改动定档，低风险 0 人、中风险 1 人、高风险 2 人；代理的批准不算人的，批准绑定具体 commit；AI 审查三轮封顶，之后只审新 diff。
- **何时用**：代理开 PR 的数量已经让逐行审查不现实，并且已经有 flag、分阶段发布和一步回滚（[[60§3.1]]、[[60§3.5]]）。
- **何时别用**：没有快速回滚和可信作者名单时，别开“低风险零人工”；原文自己也还没有指标变化时自动收紧审批的熔断器（[[60§3.5]]、[[60§4]]）。
- **来源**：[[60§3.2]]、[[60§3.4]]、[[60§3.5]]
- **相关**：精确率优先的 AI 审查器（[P25](#p25)）；多次审查投票 + 用解决率迭代（[P26](#p26)）；风险分类器代替审批弹窗（[P32](#p32)，对照：那里给单次工具调用定档，这里给整个 PR 定档）。

## P52 · 长任务的四份 Markdown：目标、里程碑、执行规则、状态日志 {#p52}

- **一句话**：prompt.md 冻结目标和完成标准，并要求先写出计划再写代码；plans.md 把工作拆成一轮能做完的里程碑，每个都写验收标准和验证命令；implement.md 写不随计划改写的执行规则（以计划为准、小步提交、每个里程碑后验证并立刻修）；documentation.md 记录状态和决策，供人隔几小时回来看。
- **何时用**：要让代理连续跑几个小时、跨很多个里程碑的从零项目或大功能（[[61§3.2]]、[[61§3.3]]）。
- **何时别用**：小改动不必写全套；原文是空仓库、全权限、“不要停下来问我”的单次实验，真实仓库里应在关键决策点保留人工确认（[[61§3.4]]、[[61§4]]）。
- **来源**：[[61§3.2]]、[[61§3.3]]、[[61§3.4]]
- **相关**：计划存进仓库，代理按清单打勾（[P22](#p22)）；Ralph 循环每轮只靠磁盘上的文件接续（[[24§3.4]]）。

## P53 · 爬分：留出集 + 一次一个补丁 + 不涨就回滚 {#p53}

- **一句话**：先验证评分器（同一输出跑两次、先人工看几条），再随机拆训练集和留出集；每轮只读训练集失败、提一个从根上修的补丁；训练涨留出不涨就当过拟合回滚；停滞两三轮先给剩余失败分类，找出坏题和评分器错误；最后停在留出集最好的版本。
- **何时用**：调提示词、skill、工具描述、模型或推理强度，想知道分数上涨是不是真的（[[62§3.3]]、[[62§3.4]]）。
- **何时别用**：评测噪声大于你在意的最小改进时先加用例或重复次数；留出集太小（原文客服例子只有 14 单）时结论要打折（[[62§3.4]]、[[62§4]]）。
- **来源**：[[62§3.1]]、[[62§3.2]]、[[62§3.4]]
- **相关**：评测的资源配置当实验变量（[P40](#p40)）；Skill 评测：小测试集 + 反例 + 确定性检查先行（[P39](#p39)）；能力评测“毕业”进回归集（[P19](#p19)）。

## P54 · 维护交给代理：一处清理一个小 draft PR，审查意见回写进 prompt {#p54}

- **一句话**：给代理一个短 prompt，写清范围、要核对的证据（历史 PR、讨论记录、开关平台、性能数据）和必须保留的东西（生产行为、killswitch、线上配置）；一处清理开一个附证据链接的小 draft PR；人审查后让代理把评论写进下一版、范围更大的 prompt；放量前在同一任务上比较贵模型和便宜模型。
- **何时用**：删死代码、清过期实验和功能开关、修 flaky test、给 CI 提速这类边界清楚、能用证据验证的维护工作（[[63§3.1]]、[[63§3.4]]）。
- **何时别用**：代理拿不到生产数据和讨论记录时，只能做静态分析那部分；原文也承认有些提案增加的复杂度超过收益，大库里候选太多要先排优先级（[[63§3.5]]）。
- **来源**：[[63§3.2]]、[[63§3.3]]、[[63§3.5]]
- **相关**：评审默认放行，阻止必附证据和解锁清单（[P44](#p44)）；Skill 的 description 写成路由合约（[P43](#p43)）；审查强度随结果递减（[P50](#p50)）。

## P55 · 审计划，不审 diff：规格逐条核对事实，再让反方试图毙掉它 {#p55}

- **一句话**：把人的审查放在计划的 PR 上。计划先经过拷问式访谈（代理给推荐答案，人推翻），写成唯一的 SPEC.md；规格里每条关于现有 API、配置、开关的说法都对照真实代码核对；再让一步专门问“有必要吗”，结论只许 BUILD、SIMPLIFY、KILL，不是 BUILD 就打回。合并后的规格交给代理实现，代理在测试门内自测自审。
- **何时用**：PR 多到人读不过来，而改动里含有别人可能反对的决策时（[[64§2]]、[[64§3.4]]）。
- **何时别用**：依赖升级、原因明显的 bug、已同意计划内的小改动不需要计划；没有足够的测试覆盖和本地可跑环境时，别让多数改动不经人读 diff 合并（[[64§3.4]]、[[64§3.5]]）。
- **来源**：[[64§3.1]]、[[64§3.2]]、[[64§3.3]]、[[64§3.5]]
- **相关**：审查分层、人工批准按风险定档（[P51](#p51)，对照：仍在 PR 上留人）；实现前由独立角色建完成标准（[P49](#p49)）；Sprint Contract（[P2](#p2)）。

## P56 · 大任务写成分阶段扇出脚本：干净上下文 + 核验阶段 + 存成命令 {#p56}

- **一句话**：任务能拆成很多独立的块、最后要一份报告时，让代理把它写成一个分阶段的脚本：每阶段扇出给上下文干净的代理，汇总前加一个独立“怀疑者”核验每条发现的阶段，进度持续保存；跑通后存进仓库，变成团队共享、带参数的命令。
- **何时用**：审一个大 PR 的每个功能、分诊最近 100 个 issue、全库审计一类 bug（[[65§3.1]]）。
- **何时别用**：任务块之间互相依赖、需要持续拆分时，看分层协调（[P31](#p31)）；来源只是产品公告，没有成本和效果数据，大规模扇出前先小规模试并看 token 用量（[[65§4]]）。
- **来源**：[[65§3.2]]、[[65§3.3]]
- **相关**：Issue 扇出 + 每个 issue 一个 worktree（[P12](#p12)）；多次审查投票（[P26](#p26)）；按专长设计子代理（[P28](#p28)）。

## P57 · 自己搭外壳从最小做起：一个循环、一个 bash、不用框架、不做代码 RAG {#p57}

- **一句话**：先写一个线性 while 循环和一个 bash 工具；观察到具体失败再加工具；工具超过约 15 个再上延迟加载；找代码用 ripgrep、glob、tree-sitter，不建向量检索；不引入通用代理框架；先单代理，能证明并行有收益再上多代理；安全规则写成数据或策略文件。
- **何时用**：给团队搭内部代理，或想理解现有代理为什么这样设计时（[[66§3.6]]）。
- **何时别用**：企业、共享或自动化场景要 OS 级沙箱和审计，不能停在最小版；需要三个以上独立轮次策略时，改成中间件流水线（[[66§3.6]]）。依据是读源码而非跑分，数字会随版本过期（[[66§4]]）。
- **来源**：[[66§3.2]]、[[66§3.3]]、[[66§3.6]]
- **相关**：用代码调用 MCP，工具按需加载（[P29](#p29)）；逐个拆脚手架（[P3](#p3)）；推理和编辑分给两个模型（[P36](#p36)）。

## P58 · 把代理接在团队已有的信号后面：标签、PR 事件、告警、每日审计 {#p58}

- **一句话**：不另造入口，而是在团队本来就会产生的信号上触发代理：工单打上 Bug 标签就先分诊、把根因写回工单；PR 打开或推新提交就审查，发现问题接着修到检查全过；告警和部署失败经 API 开会话；每天扫过去 24 小时合并的代码找规范违规。重复三次的指令写成 Playbook（结果、步骤、完成条件、纠正成见、禁止动作、所需输入）。
- **何时用**：团队的工单、聊天、监控已经集中在几个工具里，想让代理先把机械的调查做完（[[67§3.3]]、[[67§3.5]]）。
- **何时别用**：代理要碰生产数据时只给只读副本（[[67§3.4]]）；来源是厂商自述，没有准确率和失败案例，先手动跑几次再自动触发（[[67§4]]）。
- **来源**：[[67§3.2]]、[[67§3.3]]、[[67§3.5]]
- **相关**：定时代理：书签读取 + 确认后记账（[P35](#p35)）；维护交给代理（[P54](#p54)）；Skill 的 description 写成路由合约（[P43](#p43)）。

## P59 · 完成合约由程序跑，代理总结不算数 {#p59}

- **一句话**：每个短会话挂上 Done when + Verify；runner 跑检查，失败就不算完成。
- **何时用**：无人值守或多会话任务，代理爱说“做完了”。
- **何时别用**：一小时内的有界小改，边界 + 已有测试够用（[[68§3.6]]）。
- **来源**：[[68§3.3]]；对照独立完成标准 [[59§3.1]]、四份 Markdown 里程碑验收 [[61§3.3]]。
- **相关**：审计划不审 diff（[P55](#p55)）；实现前由独立角色建完成标准（[P49](#p49)）。

## P60 · 评测按执行轨迹打分，live 与 plan-only 并排 {#p60}

- **一句话**：别给闭幕演讲打分；保留 turn 结构读 tool-call；真跑与只计划两种条件一起看。
- **何时用**：代理会调工具、有权限与破坏性操作风险时。
- **何时别用**：输出本身就是唯一产物、没有工具轨迹可对的纯生成任务。
- **来源**：[[69§3.1]]–[[69§3.3]]；对照 [[19§3.2]]、[[62§3.2]]。

## P61 · 先问默认隔离，再选出站白名单与按人权限 {#p61}

- **一句话**：选型时先问“默认可不可逃出我的机器”，再写出站策略和密钥是否跟人对齐。
- **何时用**：上云端代理、自托管机队或收紧本机 CLI 沙箱时。
- **何时别用**：纯本地只读探索、无外网无密钥。
- **来源**：[[70§3.2]]、[[70§3.3]]；对照 [[51§3.1]]、[[53§3.4]]。

## P62 · 推送前看轨迹，PR 上审查加真跑，再 iterate 到绿 {#p62}

- **一句话**：critic 挡烂运行；PR 上结构化审查 + QA 真跑；draft PR 循环修到绿再给人看。
- **何时用**：代理产 PR 量大，人只想审值得合的改动。
- **何时别用**：还没有可跑的测试或预览环境时，先补验证门（见 [打地基](/guide/foundation)）。
- **来源**：[[71§3.1]]–[[71§3.4]]；对照 [[32]]、[[33]]、[[60]]。
- **相关**：精确率优先的 AI 审查器（[P25](#p25)）；多次审查投票（[P26](#p26)）；Devin 带证据交付（[[32§3.2]]）。

## P63 · effort 低档在环迭代，高档留给验证 {#p63}

- **一句话**：采访补 spec → low 实现 → 人审大方向 → high 验证和测边界；无人在环、边界又多的任务才直接开高档。
- **何时用**：常规新功能，人能在旁边快速来回时；或者棕地修 bug、安全、硬件这类边界情况多的任务（[[72§3.3]]、[[72§3.5]]）。
- **何时别用**：方向本身还没定、可能选错做法时，高档帮不上忙，失败分类里“选错理解方式”反而变多（[[72§3.3]]）；成本敏感时先测一下 max 档的花费，原文没给成本（[[72§4]]）。
- **来源**：[[72§3.2]]、[[72§3.4]]
- **相关**：对照 workshop 推荐默认 xhigh（[[03§3.5]]）；让代理边做边测的其他做法见 Peter 接上 Playwright（[[11§3.1]]）。

## P64 · 长任务开工检查：功能清单全标未通过 + 进度文件 + 先跑基础测试 {#p64}

- **一句话**：第一个会话只搭环境（JSON 功能清单、`init.sh`、进度文件、初始提交）；之后每个会话先找方位、跑一遍基础端到端测试，只做一个功能，收尾提交并写进度。
- **何时用**：任务要跨很多个上下文窗口，代理容易一口吃成胖子或过早宣布完工时（[[73§3.1]]）。
- **何时别用**：一个会话就能做完的有界小改；原文只在全栈 web 应用上试过，其他领域要自己验证（[[73§4]]）。
- **来源**：[[73§3.2]]–[[73§3.4]]
- **相关**：长任务的四份 Markdown（[P52](#p52)）；Ralph 每轮重读规格（[[24§3.2]]）；完成合约由程序跑（[P59](#p59)）。

## P65 · 派活单写满六项：只读调查并行，写操作集中整合 {#p65}

- **一句话**：每份派活写问题、归属、上下文、检查、交付物、停止条件；独立的只读调查并行，改动由主代理按依赖顺序整合。
- **何时用**：跨仓库、有共享库和共享版本锁定的迁移或升级，需要多个代理但改动彼此耦合时（[[74§3.2]]）。
- **何时别用**：任务能拆成完全独立的块、最后只要一份报告时，直接扇出更简单（[[65§3.1]]）；工作量小到协调成本超过收益时（[[74§4]]）。
- **来源**：[[74§3.2]]、[[74§3.3]]；权限边界见 [[74§3.4]]
- **相关**：迁移分支 + 依赖图分批（[[30§3.3]]）；Planner / Worker 分层（[[18§3.2]]）。

## P66 · 审查规则写成“不变量 + 触发 + 安全做法”，用三个 PR 测 {#p66}

- **一句话**：把审查者反复解释的兼容性、数据边界写进对应目录的 `AGENTS.md`；用该触发、安全反例、无关改动三个 PR 检查有无噪声。
- **何时用**：PR 多到老员工审不过来，而且有一些“diff 里看不出来”的历史约束时（[[75§3.1]]）。
- **何时别用**：格式和其他能确定性检查的东西，留给 CI 和 linter（[[75§3.4]]）；也别把 AI 审查当硬性约束，测试、分支保护和必需批准仍要保留（[[75§3.5]]）。
- **来源**：[[75§3.2]]–[[75§3.5]]
- **相关**：用 REVIEW.md 写“失败长什么样”（[[60§3.2]]）；可按仓定制的审查 skill（[[71§3.2]]）；Skill 评测里放反例（[[47§3.4]]）。

## P67 · 工人放在瓶颈阶段：强领队 + 便宜的探索工人 {#p67}

- **一句话**：先判断任务卡在“不知道要造什么”还是“写不完”；前者只把探索和规划交给便宜模型的工人，领队用强模型汇总、实现和验证。
- **何时用**：规格要靠探索才能弄清（黑盒复刻、旧系统迁移、陌生代码库），而单代理已经卡住时。ProgramBench 上只委派规划就追平三阶段全委派，成本减半；16 个 Luna 规划工人以全强队约 30% 的成本拿到相近分数（[[76§3.3]]、[[76§3.5]]）。
- **何时别用**：规格已经写清楚时，最值得委派的是实现（[[76§3.3]] 的 Commit0 对照）；领队本身弱时，配再多工人也追不上强模型单干（[[76§3.4]]）；加人只把同一份计划切得更碎时（[[76§3.5]]）。
- **来源**：[[76§3.3]]–[[76§3.5]]
- **相关**：Blocshop 贵主代理 + 便宜工人做有边界的调查（[[74§3.2]]）；Factory 验证者先探查参考程序建完成标准（[[59§3.3]]）；派活单六要素（[P65](#p65)）。

## P68 · Skill 评测分三层，Skill 多了加入口路由 {#p68}

- **一句话**：用不点名 Skill 的真实需求跑代理、读轨迹，分开测“有没有加载、有没有照做、结果对不对”；Skill 超过几个时，加一个声明“任何 X 任务都从这里开始”的入口 Skill，把关键提示放在名字和描述开头。
- **何时用**：你维护着多个 Skill 或一个插件，想知道它们在真实使用中有没有被用上时；PR 改 Skill 时用 main 和 PR 两版对比（[[77§3.2]]、[[77§3.3]]）。
- **何时别用**：只是在打磨单个 Skill 的内容时，直接调用仍然有用（[[77§3.7]]）；样本只有 10 个 PRD×3 次，入口 Skill 后相关召回仍只有 18%，别把它当万能解（[[77§3.5]]、[[77§4]]）。
- **来源**：[[77§3.2]]–[[77§3.6]]
- **相关**：name 和 description 决定触发、prompt 集里放反例（[[47§3.2]]、[[47§3.4]]）；评测按执行轨迹打分（[P60](#p60)）。

## P69 · 省钱的顺序：检查手段 → effort → 换模型，设置开头定好 {#p69}

- **一句话**：按任务而不是 token 单价算钱；先给模型一个能检查自己的测试或脚本让它少绕轮，卡住再提 effort，同一问题失败两次再换大模型；查找类子代理下放小模型；会话设置开头定好，休息前压缩。
- **何时用**：用量或账单比预期高，或者打算换模型、降档省钱之前（[[78§3.1]]、[[78§3.3]]）。
- **何时别用**：为省 token 降档或换小模型却导致重试时，省下的不够付一次重试（[[78§2]] 的开头论点、[[78§3.3]]）；价格和缓存寿命因 API、订阅、云厂商不同，要对照自己的付费方式（[[78§3.5]]、[[78§4]]）。
- **来源**：[[78§3.1]]、[[78§3.3]]–[[78§3.6]]
- **相关**：effort 低档在环迭代、高档留给验证（[P63](#p63)）；让代理边做边测（[[11§3.1]]）。

## P70 · 跟进默认排队，插话只收窄范围，权限只批最窄一档 {#p70}

- **一句话**：代理在跑时，追加的任务排队等这一轮做完；只有方向错、继续走的代价在增长时才插话，而且插话只用来收窄范围或纠正假设；审批选能让工作继续的最窄权限，不熟的命令批一次或拒绝并让它解释。
- **何时用**：一个人同时盯着几个在跑的代理，或人不在电脑前、只能偶尔做决定时（[[79§3.1]]、[[79§3.3]]、[[79§3.5]]）。
- **何时别用**：原文没有效果数据，是作者个人习惯（[[79§4]]）；可信聊天里反复出现的熟悉命令，按聊天批准更省打扰（[[79§3.5]]）。
- **来源**：[[79§3.3]]、[[79§3.5]]
- **相关**：别开全权限来躲审批（[[08§3.6]]）；`/goal` 的完成标准要可验证（[[42§3.3]]）；关掉通知、自己决定何时查看（[[27§3.4]]）。

## P71 · 缝合处用 hook 挡：一文件一写者，检查移出可写路径 {#p71}

- **一句话**：多代理事故多出在共享文件、清理和门禁，不在模型写错代码；Markdown 是建议，退出码拦截的 hook 才是硬规则——一文件一写者、先收集再清理、检查文件项目会话写不到。
- **何时用**：已经开子代理或 worktree 并行，曾出现“全绿但丢数据 / 删工作 / 代理改 CI”时（[[80§3.2]]、[[80§3.4]]）。
- **何时别用**：单代理、无共享目录时不必上全套；作者上限五并行，更大机队还要另看启动层（[[80§4]]）。
- **来源**：[[80§3.1]]–[[80§3.4]]
- **相关**：worktree 不是沙箱（[[74§3.4]]）；按效果写 hook（[P72](#p72)）；权限分类器（[[56§3.4]]）。

## P72 · 规则按效果写成 hook，开 PR 强制第二模型审查 {#p72}

- **一句话**：CLAUDE.md 点名命令挡不住副作用；把最痛的规则做成按效果拦截的 hook，并用另一模型族、只看 diff 的审查绑定到开 PR（分支 + merge-base + head），失败关闭。
- **何时用**：同一条规则反复破功，或 AI 审查后仍有逻辑 / 契约 bug 进 PR 时（[[81§3.1]]、[[81§3.3]]）。
- **何时别用**：还没有纠错记录、说不清“效果”是什么时，先记 corrections 文件；样本与工具绑定个人 Claude Code / Codex 流程（[[81§4]]）。
- **来源**：[[81§3.1]]–[[81§3.3]]
- **相关**：审查规则三个 PR 测（[P66](#p66)）；七层审查（[[60§3.2]]）；勾选要对上 diff（[[81§3.3]]）。

## P73 · 自托管并行：内部 MCP 与浏览器和写代码代理同机 {#p73}

- **一句话**：大迁移按组件拆给自托管 Cloud Agents 并行；GitHub 类工作可留在厂商托管侧，内部 MCP 和浏览器验证放在自己的机器上，避免“桌面会话必须开着”。
- **何时用**：多应用 / 多库迁移或批量重构，步骤要碰内网工具，且文件重叠可控时（[[82§3.1]]、[[82§3.2]]）。
- **何时别用**：需要每次全新强隔离沙箱时看 [[70]]；本文是厂商客户成功故事，无失败率与成本（[[82§4]]）。
- **来源**：[[82§3.1]]、[[82§3.2]]
- **相关**：Self-Hosted Machines（[[51§3.1]]）；协调代理管一群子代理（[[58§3.1]]）；依赖图上的并行调查（[P65](#p65)）。

## P74 · 行为规格给裁判、不给代理 {#p74}

- **一句话**：把“结果对也不可接受”的过程要求写成 Markdown 规格，裁判对轨迹打 true / false / NA；规格不出示给代理，假裁决只改运行时上下文。
- **何时用**：长程、高风险、结果评测贵或解释不了中间决定时（会计、合规、必须查权威来源的研究）（[[83§3.1]]、[[83§3.3]]）。
- **何时别用**：已有便宜客观测试且主要关心最终状态时，结果评测可做主干；本文无规格样例与通过率（[[83§4]]）。
- **来源**：[[83§3.3]]、[[83§3.4]]
- **相关**：按执行轨迹打分（[P60](#p60)）；实现者看不到用例（[[59§3.4]]）；Agent Evals 的 Grader（[[19§3.1]]）。

## P75 · 开工前先交未说假设，当面问开放问题 {#p75}

- **一句话**：计划核对“说过的话”和代码仍会漏产品方向；先让模型列出默认假设，主人答完再开建筑师；开放问题当面逐题问，不堆文末。
- **何时用**：大迁移 / 架构计划、多代理写计划时（[[84§3.4]]、[[84§3.5]]）。
- **何时别用**：小改动、决策已完备时不必整套管线（对照 [[68§3.6]]、[[64§3.4]]）。
- **来源**：[[84§3.2]]–[[84§3.5]]
- **相关**：拷问式访谈（[[64§3.1]]）；决策完备短会话（[[68§3.1]]）；计划作者不自审（[[84§3.1]]）。

## P76 · 为长并行对抗任务现写动态工作流 {#p76}

- **一句话**：单上下文会懒收工、偏袒自己、目标漂移；用 `agent`/`parallel`/`pipeline` 现写外壳，组合扇出、对抗核验、锦标赛等模式；常规写码多数不必上。
- **何时用**：迁移、深核验、分流、根因调查等长或对抗任务（[[85§3.3]]、[[85§3.4]]）。
- **何时别用**：token 敏感或步骤很少时；五人评审团要自己挣回成本（[[85§3.5]]）。
- **来源**：[[85§3.1]]–[[85§3.5]]
- **相关**：缝合处 hook（[P71](#p71)）；Builder+Validator（[[05§3.1]]）；多代理先算账（[[76§3.2]]）。

## P77 · 历史公开仓评测要封 git 历史并限网 {#p77}

- **一句话**：成功高分里大量是查金补丁；开跑前删 `.git` 重初始化，默认断网（仅白名单包源），并审计轨迹；报告时并列严格外壳分数。
- **何时用**：基于已修复公开 issue 的代理基准（[[86§3.1]]、[[86§3.2]]）。
- **何时别用**：评测本意包含“会用公网/历史”的真实工作流时，改用非公开仓题集并写清外壳（[[86§3.4]]）。
- **来源**：[[86§3.1]]–[[86§3.4]]
- **相关**：基础设施噪声（[[50§3.1]]）；爬分不自欺（[[62§3.1]]）；行为规格（[P74](#p74)）。

## P78 · 先塑形再实现，审查发现必须核实 {#p78}

- **一句话**：塑形对齐问题（拷问+规格+垂直切片），构建用可验证 playbook 并行，审查用专科透镜且主代理回代码核实；工具可换，环不换。
- **何时用**：一人多外壳日更、要把“理解问题”和“写代码”分开时（[[87§3.2]]–[[87§3.4]]）。
- **何时别用**：已有清晰小票且单代理能自测时，不必上全套 Skill 包（[[87§4]]）。
- **来源**：[[87§3.2]]–[[87§3.5]]
- **相关**：grill-me（[[64§3.1]]）；验证才能并行（[[26§3.1]]）；对抗式审查（[[15§3.3]]）。

## P79 · 单功能用一份 plan，别造 SDD 层级脚手架 {#p79}

- **一句话**：按量计费下，为一次功能生成 spec/plan/task 树又贵又漂、代码未必更好；用 plan mode 就地改一份计划再实现。长期 API/ADR/监管规格另算。
- **何时用**：中等功能、想先对齐再动手，又不想维护一堆产物文件时（[[88§3.2]]、[[88§3.3]]）。
- **何时别用**：规格必须活过多次实现（公开 API、合规契约）时，规格本身是资产（[[88§3.3]]）；重计划审查文化见 [[64]]。
- **来源**：[[88§3.1]]–[[88§3.3]]
- **相关**：未说假设（[P75](#p75)）；完成合约短会话（[[68§3.1]]）；RPI（[[04§3.4]]）。

## P80 · 远程 Devbox + tmux：笔记本只做控制台 {#p80}

- **一句话**：代理跑在常开远程机；本地用 SSH+tmux 附着同一会话；一任务一 worktree（可用 worktrunk）；离开前 `/goal` 写清验收。
- **何时用**：常合盖/通勤仍要并行任务，或不想本机多 clone 污染时（[[89§3.2]]、[[89§3.3]]）。
- **何时别用**：只需偶发单任务、本机已够用时；剪贴板图与多机配置同步仍要手搓（[[89§4]]）。
- **来源**：[[89§3.2]]、[[89§3.3]]
- **相关**：worktree 并行（[[23§3.1]]）；手机控制台（[[79§3.1]]）；自托管执行（[[51§3.1]]）。

## P81 · 机器人真阳性前移：开 PR 前正确性一轮 + 未推送先自审 {#p81}

- **一句话**：预审若只问规范/规格/快乐路径，机器人会挖副作用失败、双写者等另一类问题；修丁引入的机制会续租轮次。把检查清单写进 implement，triage 先审未推送修丁并设硬顶。
- **何时用**：PR 上已挂审查机器人、修 CI/评论陷入多轮时（[[90§3.2]]–[[90§3.4]]）。
- **何时别用**：还没有稳定测试门时，先补 CI（对照 [[33]]、[[22]]）；清单效果作者尚未验证（[[90§4]]）。
- **来源**：[[90§3.2]]–[[90§3.4]]
- **相关**：Bugbot 解决率（[[33§3.3]]）；CI 自动修（[[22]]）；七层审查（[[60§3.2]]）。

## P82 · 沙箱出口注入凭据，进程内不放密钥 {#p82}

- **一句话**：私有服务认证在网络出口由控制面代填；沙箱/代理环境变量里不放长期密钥。再配真终端、就绪信号与文件监视，才像“完整电脑”。
- **何时用**：云端或自建沙箱要碰私有 VCS/API，又不能信任代理持有原样密钥时（[[91§3.2]]）。
- **何时别用**：仅本机可信环境短任务；厂商 API 与快照能力因平台而异（[[91§4]]）。
- **来源**：[[91§3.2]]–[[91§3.5]]
- **相关**：Air 出站白名单（[[70§3.3]]）；短期凭据（[[48§3.2]]）；自托管网络（[[51§3.1]]）。
