# 专题：长时自主任务

<div class="hook">

**这个专题回答**：让代理连续跑几小时到几周，各家怎么处理上下文、协调、停止条件和验收？对比 4 份资料：[[24]]、[[17]]、[[18]]（含续篇 [[38]]）、[[16]]，另附 Codex `/goal` 作为参照；云端长时运行的基础设施见 [[40]] 和 [[45]]；Codex 应用里的长任务用法见 [[42]]；单个 Codex 会话连续跑 25 小时、靠四份 Markdown 不跑偏的实验见 [[61]]。

## 1. 四种做法一览

| 维度 | Ralph 循环（[[24]]） | 16 代理写 C 编译器（[[17]]） | Cursor 数百代理（[[18]]、[[38]]） | Planner / Generator / Evaluator（[[16]]） |
|---|---|---|---|---|
| **核心结构** | 外层 bash 循环反复喂同一个 PROMPT.md（[[24§3.4]]） | 每个容器一个 `claude -p` 无限循环，16 个并行（[[17§3.1]]） | Planner（可派生子 Planner）→ Worker → Judge（[[18§3.2]]）；最终版去掉 Judge，Worker 写交接报告交回 Planner（[[38§3.4]]） | Planner 扩写 spec → Generator 按 sprint 实现 → Evaluator 验收（[[16§3.2]]） |
| **上下文策略** | 每轮全新上下文；开头固定放入规格索引（有意分配），一轮只做一件事（[[24§3.2]]、[[24§3.3]]） | 每次会话全新；进度靠 README 和进度文件交接（[[17§3.1]]、[[17§3.4]]） | 每轮结束后 Judge 决定是否继续，下一轮从头开始；原文承认仍需定期重开以对抗漂移（[[18§3.2]]、[[18§4]]）；续篇加了保鲜机制：重写 scratchpad、到上限自动总结、对齐提醒（[[38§3.3]]） | 早期用 context reset；Opus 4.5 起改为 SDK 自动压缩、连续会话（[[16§3.5]]） |
| **协调方式** | 单代理，无需协调 | 无编排者：共享 git 仓库 + `current_tasks/` 锁文件（[[17§3.2]]） | 分层；锁和扁平结构在规模大时失败（[[18§3.1]]） | 代理之间通过文件交接，Generator 与 Evaluator 先协商 Sprint Contract（[[16§3.3]]） |
| **停止条件** | 外层循环不自动停；官方插件靠 Stop hook + completion promise 判断（[[24§3.4]]） | 循环持续运行，由人决定何时结束 | Judge 决定是否进入下一轮（[[18§3.2]]）；续篇中 Judge 被删掉，Planner 收到交接后持续规划（[[38§3.3]]、[[38§3.4]]） | Evaluator 按契约标准判定，任一标准低于阈值即打回（[[16§3.2]]） |
| **谁来验证** | 测试与外层确定性检查（[[24§3.5]]） | 高质量测试集 + GCC 作为 Oracle（[[17§3.3]]、[[17§3.5]]） | Judge 代理 | 单独调教的 Evaluator，用 Playwright 操作真实应用（[[16§3.4]]） |
| **规模与成本** | 直播结束时循环仍在跑，未给出结果和成本（[[24§4]]） | 近 2,000 个会话，总成本略低于 $20,000，10 万行 Rust 编译器能构建可启动的 Linux 6.9（[[17§4]]） | 浏览器项目近一周、100 万+ 行；成本未给出，只说“数万亿 token”（[[18§4]]）；续篇：峰值约每小时 1,000 次提交、一周约 1,000 万次工具调用（[[38§4]]） | 复古游戏编辑器：单代理 20 分钟 / $9（游戏是坏的） vs 完整 harness 6 小时 / $200；DAW 实验见原文（[[16§4]]） |

## 2. 对照参考：Codex `/goal`

`/goal` 把“没做完就说做完了”交给 harness 处理：目标没达成时自动推模型继续，模型调用 `update_goal` 才结束（[[09§3.6]]）。OpenAI 讲者的建议是完成标准要尽量可验证，并在里程碑处做“目标审计”（[[42§3.3]]）。OpenAI 在内部也用它跑长任务（[[10§3.5]]）。Grok Build 的 `/goal` 再加一个 skeptic 代理证伪（[[15§3.3]]）。

## 3. 关键分歧

### 压缩、重置，还是每轮全新上下文？

- **全新上下文**：Huntley 认为压缩有损，每轮重开、重读规格（[[24§3.4]]）；C 编译器实验的每个代理也在没有上下文的新容器里醒来（[[17§3.4]]）。
- **自动压缩**：Anthropic 换到 Opus 4.5 后去掉 context reset，跑成一个连续会话（[[16§3.5]]）；Codex 服务端自动压缩（[[09§3.7]]）。
- **频繁有意压缩**：RPI 在每个阶段结束时主动把成果写成文档（[[04§3.4]]）。

三者的共同点：**进度要落在文件里，而不是只活在会话里**。OpenAI 的 25 小时 Codex 实验把这一点写成了四份文件：目标、带验证命令的里程碑、执行规则、状态日志（[[61§3.2]]–[[61§3.4]]）。差别在于“交接”发生的频率，以及交给模型自己做还是交给外层脚本做。

### 扁平还是分层？

C 编译器实验用锁文件 + 扁平结构跑通了 16 个代理（[[17§3.2]]）；Cursor 在数百代理时发现同样的做法失败，改为分层，并发现专门的 integrator 反而是瓶颈（[[18§3.1]]、[[18§3.4]]）。

### 要求每步都对吗？

Cursor 发现，要求每次提交都 100% 正确会让数百代理的系统串行化，于是接受小而稳定的错误率，最后用一个“green”分支做修复（[[38§3.5]]）；C 编译器实验则强调测试和验证器要近乎完美（[[17§3.3]]）。两者针对的环节不同：中间状态可以放宽，最终验收不能。

### 停在哪里？

外层循环（Ralph、C 编译器）把“停”交给人或外层脚本；`/goal`、Stop hook、Judge、Evaluator 把“停”交给一个判断者。Huntley 直播里唯一能观察到的差异，是官方插件版在第一轮后就宣告完成、停止了循环（[[24§4]]）。

Factory 的实验把“停在哪里”问题量化了：单代理在 gdal 上自己判断做完时只复现了 36%，每个单代理运行都是自己决定结束、不是预算用完；改成由独立验证者事先建好完成标准、编排者决定何时交付后达到 90%（[[59§3.1]]、[[59§3.5]]）。

## 4. 共识

1. **验证决定上限**：C 编译器靠测试和 Oracle，Anthropic 靠 Evaluator，Cursor 靠 Judge。作者 Carlini 的提醒是：测试通过很容易让人以为工作完成了，而事实很少如此（[[17§4]]）。
2. **规格要清晰**：规格错了，循环只会高效地放大错误（[[24§4]]）。
3. **隔离环境**：无人值守 + 放开权限，必须在隔离环境里跑（[[24§3.1]]、[[17§3.1]]）。
4. **运行要能断点续跑**：跑几天的任务一定会遇到机器或 API 故障。Cursor 云端代理把代理循环放进 Temporal 持久化执行，并拆成多个短 workflow（[[40§3.2]]）；Anthropic 把事件日志放在 harness 之外，harness 崩溃后从日志恢复（[[45§3.2]]）。
