## 1. 需求说不清楚，怎么办？

- **让代理反过来采访你**。Arno 的观点是：比起你自己把需求说清楚，Claude 更擅长从你身上把需求挖出来（[[03§3.1]]）。Peter Steinberger 的关键提示也是先让模型提问（[[11§3.3]]）。
- **找出“没写下来的东西”**。Thariq 用“地图不是疆域”和四象限描述代理会撞上的未知，并给了五种挖掘手法，每种都有可照抄的 prompt（[[06§3.3]]、[[06§3.4]]）。
- **让代理带着推荐答案拷问你，由人推翻**：Giant Swarm 的 `/grill-me` 沿决策树问遍每个问题，每问附推荐答案、事实自己去查；被人推翻的推荐，就是人的上下文起作用的地方。他们建议两三个人一起拷问一份计划（[[64§3.1]]）。
- **用可看的原型代替文字讨论**：Arno 用 HTML 而不是 Markdown 做设计探索（[[03§3.2]]）。

## 2. 计划要写到什么程度？

- **分阶段、每阶段产出文档**：RPI 把工作分成 Research → Plan → Implement，计划里写清文件名、代码片段和每步怎么测试（[[04§3.4]]）。
- **写明边界和完成标准**：Grok Build 的 plan mode 会自己探索目录、读说明文件，再弹出可交互的计划，里面有 non-goals 和成功指标（[[13§3.2]]）。
- **把“可验证”设计进计划**：Arno 让组件输出供代理和 CI 核验的契约，验证从设计阶段就开始（[[03§3.3]]）。
- **把计划存进仓库，代理按清单打勾**：Gemini CLI 的 Conductor 先用 setup 写下产品、技术栈和团队流程（[[29§3.1]]），每个需求生成 `spec.md` 和 `plan.md`（[[29§3.2]]），执行时逐项打勾，中途停下也能接着做（[[29§3.3]]）；团队纪律（TDD、覆盖率、技术栈变更流程）写进 `workflow.md` 模板（[[29§3.4]]）。
- **长任务的计划要拆成“一轮能做完、能自己验收”的里程碑**：Codex 跑 25 小时的实验里，prompt.md 先冻结目标并要求“写出 plans.md 之前不许写代码”（[[61§3.2]]）；plans.md 的每个里程碑都写范围、关键文件、验收标准和验证命令，失败先修再往下走（[[61§3.3]]）。
- **规格里关于现有代码的说法逐条核对，再让一步专门试图毙掉计划**：Giant Swarm 的 `/ground-truth` 把每条关于 API、配置、开关的说法对照真实代码核对，示例里抓到一个编造的配置键；`/contrarian` 只问“有必要吗”，结论只有 BUILD、SIMPLIFY、KILL，多数计划回来是 SIMPLIFY（[[64§3.2]]、[[64§3.3]]）。
- **按难度选流程强度**：小改动不必走全套（[[04§3.7]]）；Giant Swarm 的门槛是“改动里含有别人可能反对的决策，才写计划”（[[64§3.4]]）。

## 3. 计划谁来读？

- **人读计划，而不是读每一行代码**：计划里的一处错误可能变成 100 行坏代码，调研里的一处错误会毁掉整件事（[[04§3.6]]）。
- **把审查从代码 diff 挪到计划 PR**：Giant Swarm 的 PR 一年涨到三倍，人改为在计划的 PR 上争论、拍板、合并；代理照合并后的规格实现，在测试门内自测自审，多数代码 PR 不再有人逐行读。前提是测试覆盖率、本地能跑的环境和早而具体的反馈（[[64§3.5]]）。
- **先审批再动手**：plan mode 可以批准、修改或放弃计划，批准后才自动开始实现（[[13§3.2]]）。
- **做完再对照计划审一遍**：Conductor 的自动审查会检查每个阶段是否完成、有没有漏掉 spec 里的核心需求（[[29§3.5]]）。
- **大任务的计划要拆到“一个代理一次做完”**：并行编排时，子任务要能放进一个提交、能快速验证、依赖清晰（[[30§3.4]]）。

## 4. 阶段之间怎么交接上下文？

- **把上下文当稀缺资源**：上下文是唯一的杠杆（[[04§3.1]]）；用到约 40% 后效果递减（[[04§3.2]]）；子代理用来隔离搜索过程，而不是扮演角色（[[04§3.3]]）。
- **有意压缩**：每个阶段结束时主动把成果写成文档，下一阶段从干净会话开始（[[04§3.4]]）。
- **把计划、规则和状态分成不同文件**：prompt.md 管目标，plans.md 管里程碑和决策记录，implement.md 是不随计划改写的执行规则，documentation.md 是人离开几小时后回来看的审计日志（[[61§3.4]]）。
- 规则文件和 Skills 这类“每次开工都要有”的上下文，见 [打地基](/guide/foundation)。

## 5. 来源之间的分歧

| 议题 | 观点 A | 观点 B | 怎么理解 |
|---|---|---|---|
| 项目知识要不要写成固定文档 | Dex Horthy：维护 onboarding 文档会越写越长、会过时，更推荐每次按需生成压缩的研究文档（[[04§3.5]]） | HumanLayer：把细节拆成 `agent_docs/` 里的固定文件，按需读取（[[20§3.5]]）；Conductor：产品、技术栈、流程各写一个文件，随新功能持续更新（[[29§3.1]]） | 两者都反对把一切塞进根规则文件。差别在于细节是“维护好放着”还是“用时现查”。变化快的部分更适合现查，稳定的构建、测试说明更适合写成文件。 |
| 计划审过之后，人还要不要读代码 | Giant Swarm：对照已同意的规格和测试门，更信代理的审查，多数改动不经人读 diff 合并，碰到公共 API 和安全时人再看（[[64§3.5]]） | Claude Code 团队：每个 PR 仍按风险分档决定要几个人批准（[[60§3.4]]）；RPI：人读计划，但计划本身要写到文件和代码片段（[[04§3.6]]） | 两边都把人的注意力往前移，差别在“代码这一关要不要固定留人”。Giant Swarm 没给出不经人读合并后的出错数据；要照做，先把测试门和本地环境做扎实。 |
| 上下文满了怎么办 | RPI：频繁有意压缩，阶段之间写文档交接（[[04§3.4]]） | Ralph：每轮全新上下文，认为压缩有损（[[24§3.4]]）；Anthropic 长任务 harness 换到 Opus 4.5 后去掉了重置，改用自动压缩（[[16§3.5]]） | 详见[长时自主任务专题](/guide/long-running)。共同点是：**不要让一个会话无限变长**。 |
