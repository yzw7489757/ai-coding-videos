# 总预算钉死时，多分几个代理会更快吗？

<div class="meta-tags"><span class="tool-tag tool-general">通用（不限工具）</span></div>

<div class="hook">

**一句话看懂**：UK AISI 与伯克利 / 微软的工作显示，同预算下并行（再加留言板通信）往往更好。Generality Labs 在 MirrorCode 的 3 个任务上，把 **250M token 总预算均分**给 1–64 个共享沙箱、可留言的代理：Ruff 上 8 代理是甜点（更快，有时更好），Cprepro 终分却是单代理更优；更大团队常因协调失败变慢，8 代理平均只贵约 1.1%。

</div>

## 读完你能带走的 7 条收获

1. **改的是预算怎么分，不是换模型**：总预算固定 250M，按队规模均分；单代理触顶只杀自己，全员用尽才算该样本结束（见 3.1）。
2. **通信介质是无限制留言板**：全局板 + 私信，工具调用间隙提示未读；同模型常撞名、要多轮改名才能入板（见 3.1）。
3. **Ruff 上 8 代理是平均最佳**：相对单代理，平均曲线多过 30.5% 测，达相同分数约 6.1× 更快；摘要里 GPT-6.1 Sol 达 98% 测 6.9× 更快，Haiku 5.5 达单代理最佳分 16.0× 更快且终分高 19.2 个百分点（见 3.2）。
4. **换任务就不成立**：Cprepro 上 Haiku 5.5 与 GPT-6 Luna 终分**单代理更好**；Sed 太易饱和，加速更弱——需要足够难度与时间跨度（见 3.3）。
5. **队越大未必越快**：到 64 常回升耗时、过更少测；作者归因协调失败，且硬件随 N 加配（见 3.3、3.4）。
6. **成本几乎不跟着 N 线性涨**：全记录里 8 代理平均每跑只贵 1.1%；64 平均贵 24.8%（更偏贵的输出 token；长上下文加价也搅局）（见 3.4）。
7. **作者自己限制外推**：假设 MirrorCode 比许多真实任务**更适合**这种委托，真实工作里增益可能没这么显眼（见 3.3、4）。

::: tip 小白先懂这几个词
- [Harness（代理外壳）](/glossary#harness)：模型外负责工具、循环、上下文——以及本文里的留言板与预算切割——的那一层。
- [MirrorCode](/glossary#mirrorcode)：Epoch AI 的长程软件复刻基准；代理不见源码，要重建程序行为，按可见 / 隐藏测试通过率打分。
- Token 预算：把对话累计的 input + output token 当作硬上限；触顶则该代理终止。
- [Message Board（留言板）](/glossary#message-board)：团队共享的通信面；本文无条数限制，含全局与私信。
- 并行搜索 vs 通信并行：前者同预算多次独立尝试；后者允许代理中途交换信息（UK AISI / Berkeley–Microsoft 对照的起点）。
- Ruff / Cprepro / Sed：本文选的三个 MirrorCode 任务（Python linter、GCC C 预处理器、流编辑器），难度递增不等。
:::

## 2. 这篇在回答什么

如果你只有一笔固定的推理预算，是全给一个代理慢慢啃，还是切成 N 份让大家并行、还能在留言板上说话？

UK AISI 已报告：同总预算下，拆成多次独立尝试往往更好。伯克利与微软再加上**共享留言板**，发现能通信的并行又胜过纯并行搜索。Generality Labs 把问题推到 MirrorCode——Epoch AI 的长程复刻基准：代理必须在不见源码的情况下重建整个程序，连边角行为也要对，分数是可见与隐藏测试的通过百分比。

他们选了难度不同的 Ruff、Cprepro、Sed，队规模取 1、2、4、8、16、32、64，**总预算钉死 250M token 并均分**。

这篇文章主要回答：

1. 预算、终止与留言板具体怎么规定？
2. 加速与“能力解锁”在 Ruff 上有多强？
3. 换 Cprepro / Sed 还成立吗？大团队为何变慢？
4. 多出来的速度贵不贵？能外推到真实工程吗？

## 3. 怎么做

### 3.1 固定总预算怎么切，代理怎么说话

**是什么**：预算按对话累计的 input + output token 计算。每个代理有自己的份额；**一个耗尽不会停掉整队**。停工会被唤醒，且必须用尽自己的预算。队内全部用完，该队规模的样本才算完成。

250M 除以队规模：人越多，每人越瘦。代理共享**一台** computer sandbox 与其中的文件。更大的队会配更多硬件（脚注：1 代理 1.25 vCPU / 2.25 GiB，一路加到 64 代理 17 vCPU / 18 GiB）。作者写明未来会让所有队规模用同一套硬件——读现在的速度数字时，要把“加人又加机”记成混杂因素。

通信：留言板做进 harness，**没有条数或内容限制**；可上全局板，也可私信。加入时自选名字——同一模型常常选中同一个名字，撞车就要再想新名，不少 run 为此多耗几轮。工具调用之间，模型会收到未读条数提示。文中还给了 GPT-6.1 Sol、64 代理、Ruff 任务上 128× 回放可视化。

**为什么这样设计**：继承“同预算并行探索”与“通信优于哑巴并行”两条线，问的是——在**必须复刻整程序**的长程题上，均分预算的团队曲线长什么样。脚注也强调：这种“把原给单代理的预算拆给协作代理”的改法，理论上可套到任意 agent 任务；它改的是**预算分配方式**。

### 3.2 Ruff：8 代理甜点，加速与分数一起动

作者开篇就给了力度最大的数字：

::: tr 我们看到加速的强证据，以及能力解锁的暗示性证据。
> "We find strong evidence of acceleration, and suggestive evidence of capability unlocks."
:::

具体到摘要：用 8 个代理替代 1 个时，GPT-6.1 Sol 在某一 MirrorCode 任务上达到 98% 单测通过，比其单代理基线快 **6.9×**；Haiku 5.5 达到单代理基线最佳分快 **16.0×**，且终分高 **19.2** 个百分点。紧接着限制句：这些结果**并非**在每个测过的 MirrorCode 任务上都成立。

Ruff 章节的平均曲线：按平均终分，**最佳队规模是 8**——多过 **30.5%** 的单测，并在达到与单代理相同分数时约 **6.1×** 更快。最优 N **强烈依赖模型**；到 64 这种规模，有的模型反而更慢、通过更少。

我觉得这里最有用的读法是：先信“加速”，对“解锁更高分”保持作者自己的 *suggestive* 力度——而且只挂在 Ruff 这类题上。

### 3.3 Cprepro / Sed：终分与饱和告诉你边界

**Cprepro**：Claude Haiku 5.5 与 GPT-6 Luna 各 3 个 epoch。结果：**单代理终分优于多代理**；但在冲早期通过率百分比时，多代理仍然更快。

**Sed**：同一对模型各 3 epoch。这题明显更容易，多数组合很快饱和（除了 Luna 的 64 代理）。仍能看到一些加速，但更弱。作者判断：多代理要划算，任务得有**足够难度与时间跨度**。

里程碑图（达到某一通过率所需时间 vs 队规模）画出收益递减：加人后时间台阶式下降，接近 64 又往上翘；拐点因模型而异。

外推上作者很老实（脚注）：

::: tr 我们假设：MirrorCode 这类基准特别适合协作代理式的委托，胜过其他基准和真实任务，因此这些结果在真实工作中很可能没那么显眼。
> "Note that we hypothesise that MirrorCode as a benchmark is specifically more amenable to this sort of delegation from collaborating agents than other benchmarks and real-world tasks, so these results are likely less prominent with real work."
:::

### 3.4 成本：8 代理几乎不贵，64 开始胀

全记录平均：八代理团队每跑只比单代理贵 **1.1%**。队越大，越偏向更贵的 **output** token；**64** 代理平均贵 **24.8%**。奇怪的是有的模型加人后账单反而更低——作者猜测与厂商对长上下文加价有关：例如 Anthropic Haiku 5.5 在 prompt 超过 100K token 后输入 / 输出价 ×5；OpenAI 若干型号在超过 272K 后整次请求输入 ×2、输出 ×1.5。多代理把上下文摊薄，有时能躲开加价档。

三维权衡图的叙述是：大致可以多花钱换更快；但**协调失败**会挡住大团队拿到高分。

结论段收束为：把 MirrorCode 的 token 预算分给多个代理，能让模型在**某些**任务上快得多，有时也好一点，但**推不到每一个** MirrorCode 任务。令作者惊讶的是：只改 harness 里如何分派预算，就能大幅缩短时间，又几乎不抬成本。最优代理数取决于模型与任务；加人不是单调更好。

## 4. 结果与局限

**文中真正给出的结果**：

- 250M 均分规则、终止与留言板机制；硬件随 N 变化的脚注表。
- Ruff：8 代理平均 +30.5% 测、同分离 6.1×；摘要中 6.9× / 16.0× / +19.2pp。
- Cprepro 终分单代理更好；Sed 易饱和、加速较弱。
- 8 代理 +1.1% 成本；64 代理 +24.8%；长上下文加价说明。

**局限与注意**：

- 硬件与队规模耦合（作者承认，未来会对齐）。
- 交互图细节依赖页面脚本；本文只采用正文写明的数字。
- “能力解锁”为暗示性证据；Cprepro 直接反对“多多益善”。
- MirrorCode 可能特别适委托——真实仓库里的接口、权限、代码所有权冲突，文中未测。
- 日志需联系作者获取，第三方难逐 run 复核。

## 5. 结论

这篇证明的是一件很具体的事：**在固定总预算下，把“一个胖子代理”改成“一群能留言的瘦代理”，有时是几乎不加钱的加速旋钮——但最优人数看模型与任务，加到 64 还可能更慢。** 它不是生产环境的分工手册；和站内讲缝合处失败、主代理管依赖图的文章（[[80]]、[[74]]）合读时，一边看受控扩展曲线，一边看真实协调税。

**你可以这样试**

1. 选一个已有单代理基线的长任务，钉死总 token（或总美元）预算，试 N=1/4/8，只改均分与是否共享工作区。
2. 先给一个极简留言板（全局 append-only 日志也行），看未读提示会不会变成噪声。
3. 记录的不只是终分，还有“第一次到达 50% / 80% 测”的时间——文中加速常出现在前半段。
4. 若你的任务像 Cprepro 那样难拆，把终分掉下去当成信号：先改善可委托边界，再加人。

**读完自测**

1. 一个代理用尽自己的 token 后，整队会不会立刻停？
2. Ruff 与 Cprepro 对“多代理是否更好”的答案差在哪？
3. 为什么作者说 8 代理几乎不贵，仍要警惕 64 代理？
