# 行为规格不给代理看：Basis 怎么评长程会计代理

<div class="meta-tags"><span class="tool-tag tool-cursor">Cursor</span></div>

<div class="hook">

**一句话看懂**：Basis 做给会计师用的长程代理（月结、合伙企业税表、审计准备），从第一天就在 Cursor 里改代理读到的上下文。他们的关键做法是 **behavior spec（行为规格）**：一份给人和裁判看的 Markdown，写清某种情境下代理该检查什么证据、做什么决定——**它不是提示词，也不发给代理**。裁判拿规格 + 可观察轨迹判 true / false / NA，用来补上“只看最终税表对不对”的盲区。

</div>

## 读完你能带走的 7 条收获

1. **长程 ≠ 跑得久**：是轨迹上成百上千个依赖前面的决定；早期错误会污染后面，而最终结果未必暴露起点（见 3.1）。
2. **会计场景三难**：便宜客观测试少、真实 ground truth 贵、最终结果要几小时到几天才审得完（见 3.1）。
3. **结果对也可能过程不可靠**：没查权威来源却算对、抽出对数字却没保留出处、做出能用的表却不可泛化（见 3.1）。
4. **上下文是生产输入**：自然语言的组织与措辞会改变下一步行为；生成后不读就上线是生产风险（见 3.2）。
5. **行为规格给裁判、不给代理**：写清适用时机、证据、决定、动作、证据不足时怎么办、失败长什么样；裁判输出 true / false / NA（见 3.3）。
6. **开发闭环：规格 ↔ 运行时分离**：假裁决指出实现缺口，改的是运行时上下文 / 工具 / 框架，规格仍是标准（见 3.4）。
7. **生产量级**：单次交付物上代理可做 5+ 小时；Form 1065 大约人 30–40 小时、代理约 6–7 小时；顶 25 家事务所中约 40% 信任使用（见 3.5）。

::: tip 小白先懂这几个词
- [Trajectory（轨迹）](/glossary#agent-trajectory)：一次任务里代理的可观察过程——工具调用、产物、检索来源、决定记录。
- [Behavior Spec（行为规格）](/glossary#behavior-spec)：写给人和裁判的 Markdown 标准，**不**作为提示词发给代理。
- [Outcome Evaluation（结果评测）](/glossary#transcript-outcome)：只看最终交付物对不对；长程任务上贵，且解释不了中间每一步。
- [Harness（代理外壳）](/glossary#harness)：提示词、Skills、工具说明、内存等围绕模型的整套上下文与循环。
- Judge（裁判）：读规格与轨迹、输出 true / false / NA 的评分器（人或模型）。
:::

## 2. 这篇在回答什么

税表最后数字对了，你怎么知道代理是查了一级权威来源，还是碰巧蒙对？长程会计任务上，只做结果评测又贵又盲。

Basis 的回答是：把**反复出现的行为**写成规格，用裁判在真实轨迹上打点；规格与代理读到的提示词分开。Cursor 则是他们读写这些 Markdown 上下文的地方。

## 3. 怎么做

### 3.1 为什么“最终结果对不对”不够

长程不只是代理跑好几小时，而是轨迹上**成百上千个决定**，后面的步骤常常依赖前面的。系统要保存相关状态、消化工具结果、从失败里恢复，有时还要跨过单次上下文装不下的信息。错误会累积：早期失误影响后面的检索、计算、工具调用和产物，而最终结果未必暴露问题从哪开始。

会计把这件事变得更难，原文给了三条：

1. 许多结果没有便宜、客观的测试；
2. 从真实生产工作抽出的 ground-truth 样例又贵又难扩；
3. 一个最终结果可能要几小时到几天才能做完并审完。

即便最终结果正确，也可能藏着不可靠过程：没查研究权威却做出正确税表、抽出正确数字却没保留来源、做出能用的工作簿但过程不可泛化。结果评测仍然重要，但贵，而且**解释不了长轨迹里每一个关键决定**。

### 3.2 上下文是生产输入，要像代码一样读

代理的最终输出只是系统的一部分。行为还取决于全程收到的上下文：说明、领域知识、例子、工具描述、Skills、内存和其他运行时信息。这些是自然语言，工程师必须读。

传统程序对同一段合法代码解释不变，不怎么在乎文件排得漂不漂亮。语言模型则不同：**上下文的组织和措辞会改变模型下一步做什么**。一句含糊的话、一条被埋住的例外、一个误导性例子，都能改变生产行为。生成一份上下文文件却不读就上线，是生产风险。

### 3.3 行为规格：标准写清楚，且不给代理看

行为规格是一份 Markdown，定义代理在特定情境下应有的反复行为。它写给人、以及审查录制轨迹的裁判。原文把边界划死：

<Trans zh="它不是提示词，也不会出示给代理">“It is not a prompt, and it is not shown to the agent.”</Trans>

有用的规格要写清：何时适用、应检查什么证据、应做什么决定、随后什么动作、证据不全时怎么办、失败长什么样。目标是让行为**可裁判**，而不是把每一步脚本化。

裁判拿到规格、可观察轨迹和证据（工具调用、产物、检索来源、决定记录），返回 **true、false 或 NA**。这样可以在没有整任务完整 ground truth 的情况下，评测过程中选中的片段。

Mitch Troyanovsky 把动机说成：

<Trans zh="一个正确的税务答案仍可能藏着糟糕的过程。我想知道代理有没有查一级权威，而不只是申报表对不对。规格就是我们用来裁判这一点的东西">“A correct tax answer can still hide a bad process. I want to know if the agent checked primary authority, not just if the return is right. The spec is how we judge that.”</Trans>

我觉得这和 [[69§3.1]]“按执行轨迹打分、别给闭幕演讲打分”、[[59§3.2]]“实现者看不到用例”高度同向：标准若泄漏给被测代理，代理会优化标准的字面，而不是优化你真正在乎的行为。和 [[19]] 的 Grader、[[62]] 的评分器校验可以一起看——这里强调的是**规格与提示词分库**。

### 3.4 在 Cursor 里改规格，在运行时里量是否达标

Basis 用 Cursor 构建和打磨代理：工程师打开 Markdown 规格，检查某句是否太含糊或太脆，改完在同一窗口预览；同一环境里也改代理真正读到的 Skills、说明、工具描述。联合创始人强调的是能检视并改写塑造行为的上下文：

<Trans zh="Cursor 是我们检视塑造代理的上下文、并改到行为站得住的地方">“Cursor is where we inspect the context that shapes the agent, and revise it until the behavior holds.”</Trans>

开发闭环原文写成七步：

1. 团队认定一种值得测量的反复行为；
2. 工程师在 Cursor 里写或改行为规格；
3. 代理在生产中干活，留下录制轨迹；
4. 裁判按规格评每条行为，返回 true / false / NA；
5. false 指出“意图中的行为”与“运行时实现”之间的缺口；
6. 团队更新运行时上下文、工具、提示词或执行框架——这些措辞仍在 Cursor 里改；
7. 再跑代理，测量行为是否改善。

**规格与运行时保持分离**：规格是标准；实现一直改到代理稳定达到它。该做法来自 Basis 做生产会计代理的经验；Basis 与 Braintrust 把它发成开放格式，方便其他团队用同一通用结构定义和评行为。

### 3.5 生产上的量级（口述数字）

文中给出的生产侧陈述：

- 单次交付物上，Basis 代理可做 **5+ 小时**工作；
- Form 1065 合伙企业申报：人大约 **30–40 小时**，Basis 代理大约 **6–7 小时**；
- 顶 25 家事务所中约 **40%** 信任使用，更广的领先事务所也有客户。

页面还写合伙企业税表可快至约 6 倍，并强调最强证据是工作本身：代理在长轨迹上做大量决定，交付物由专业会计师审阅使用。

## 4. 结果与局限

**文章真正讲清的方法**：

- 长程会计任务上，过程行为评测补结果评测；
- 行为规格的定义、不给代理看的纪律、裁判三值输出；
- 规格 ↔ 裁判 ↔ 改运行时的闭环，以及与 Braintrust 的开放格式声明。

**局限与注意**：

- **客户故事**：Cursor 产品能力（预览、切模型）着墨较多，裁判模型、通过率、规格样例正文几乎不给；
- **数字不可核对**：6×、40%、5+ 小时、30–40 / 6–7 无评测协议；
- **开放标准**：文称与 Braintrust 发布，本文没有规格 schema 全文，落地需另查；
- **领域特殊**：无便宜客观测试的假设对有强测试的代码任务不总成立——那时结果评测仍可做主干，行为规格作补充。

## 5. 结论

代理轨迹越长，只看最终交付物越容易被“碰巧做对”骗到。Basis 的做法是：把你在乎的反复行为写成**不给代理看的规格**，用裁判在真实轨迹上打 true / false / NA，假的那一侧指引你改运行时上下文，而不是改标准去迁就实现。

**你可以这样试**

1. 选一个你已有结果评测的任务，列出 3 条“结果对也不可接受”的过程要求（例如必须打开某类权威来源、必须保留数字出处）。
2. 写成短 Markdown 规格，明确适用条件与失败样貌；**不要**把它粘进代理系统提示。
3. 抽 10 条历史轨迹（或新跑 10 次），用人或模型裁判打 true / false / NA；只针对高频 false 改 Skills / 工具说明，再测一轮。

**读完自测**

1. 为什么行为规格不能发给代理？
2. 裁判返回 NA 是干什么的？
3. “规格与运行时分离”和“把完成标准写进同一份 prompt”有什么差别？
