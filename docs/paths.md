# 🧭 学习路径

<div class="hook">

不知道从哪读起？按你现在的水平选一条路径。左侧边栏是按任务阶段（打地基 → 做规划 → 单代理推进与一人多线 → 多代理协作与大任务拆分 → 验收这一次的产出 → 评测代理本身与给动作把关 → 接进 PR 与 CI → 云端与后台运行环境 → 看原理）组织的“目录”，这里是按难度组织的“读法”。每条 9–22 步，顺序是“先懂概念 → 跟着做 → 再扩展”。每一步都写了**读完能带走什么**。

</div>

::: tip 怎么用
- 每一步都可以只读文章开头的“一句话看懂”“收获清单”和第 5 节“结论”，有兴趣再看全文。
- 不认识的词，点文章里的蓝色链接跳到[术语表](/glossary)。
- 每条路径最后都有一个“动手练习”，来自对应文章的“你可以这样试”。
:::

## 🌱 新手：让一个代理靠谱地干活 {#beginner}

适合：刚开始用 Claude Code、Codex、Cursor 等编码代理，或者用过但觉得“时灵时不灵”。

| 步骤 | 读什么 | 读完能带走什么 |
|---|---|---|
| 1 | [[27]] | 一条从怀疑到熟练的路线：先换工具形态，再用重做自己的活来建立直觉 |
| 2 | [[20]]，再看 [[28]] 和 [[46]] | 规则文件只写每次都用得上的内容，细节用指针；必须每次执行的规则写成 hook，配置可以直接抄；Grok Build 的自动记忆给出了“该记什么、不该记什么”的标准 |
| 3 | [[04]] | 上下文是稀缺资源；Research → Plan → Implement 分阶段推进 |
| 4 | [[25]] | 三句能马上用的测试提示词：red/green TDD、先跑测试、手动测试 |
| 5 | [[48]] | 把第一个小任务交给云端会话：一个任务一台机器，prompt 里写清怎么证明做完了 |
| 6 | [[21]] | Skills 是什么、为什么按需加载 |
| 7 | [[03]] 或 [[06]] | 让代理采访你、用原型挖出没说清的需求 |
| 8 | [[72]] | `/effort` 怎么选：采访补 spec → low 实现 → 人审方向 → high 验证；高档帮的是漏边界，不是方法错 |
| 9 | [[78]] | 一个任务的钱花在哪：每轮重发整段对话、缓存命中率最关键；先加检查再提 effort，任务结束用 `/usage` 看三件事 |

**动手练习**：在自己的项目里新开一个会话，第一句话写 “First run the tests”，再按 [[20]] 的建议把 CLAUDE.md / AGENTS.md 删到只剩通用内容。

**延伸阅读**：[打地基](/guide/foundation) · [做规划](/guide/planning) · [单代理推进与一人多线](/guide/solo)

## 🚀 进阶：并行与自动化 {#intermediate}

适合：已经能让单个代理稳定完成任务，想同时推进多件事，或者把代理接进 PR 和 CI。

| 步骤 | 读什么 | 读完能带走什么 |
|---|---|---|
| 1 | [[23]] | issue → worktree → PR 的并行流程，以及端口、依赖、数据库的隔离办法 |
| 2 | [[22]] | `codex exec` 管道和“密钥与写权限分离”的 CI 布局 |
| 3 | [[01]] | 把代理挂到事件流上；验证就是“代理能不能把东西跑起来” |
| 4 | [[02]] | Claude Code 团队自己的工作流：从本地到云端、扇出 + 对抗式复核 |
| 5 | [[10]] | 团队级的 PR 审查与 CI 看护 |
| 6 | [[26]] | 并行之前先补验证：给代码库的 8 根验证支柱打分 |
| 7 | [[33]] 或 [[31]] | 常驻 PR 审查机器人怎么衡量（解决率）、为什么审查要精确率优先 |
| 8 | [[41]] | 定时代理怎么设计才不会悄悄出错：书签、读失败要明说、确认后再记账、最小权限和花费上限 |
| 9 | [[42]] | Codex 应用里 Computer Use、`/goal`、子代理、线程交接和自动化分别什么时候用 |
| 10 | [[37]] → [[40]] | 后台 / 云端代理要什么样的环境和基础设施：统一开发入口、自愈环境、持久化执行 |
| 11 | [[47]]，再看 [[77]] | 给团队的 Skill 写一套小评测：反例、确定性检查、固定格式的风格评分；Skill 多了以后先测“会不会被找到”，加入口路由 Skill，留意目录截断 |
| 12 | [[51]]，案例再看 [[82]] | 云端代理需要碰内网时把执行放进自己的网络；Navan 用自托管 Cloud Agents 并行迁多个应用，内部 MCP 与浏览器同机 |
| 13 | [[70]] | 对照五种跑法的默认隔离；Air 的出站白名单与按人权限（组织预览） |
| 14 | [[55]] | 把维护流程写成仓库里的 Skills：AGENTS.md 规定何时必须用，description 决定何时想到用，本地跑稳再上 CI |
| 15 | [[57]] | 改 CLAUDE.md、skills、hooks 时在 CI 里跑评测：eval JSON、workflow、check.sh 三个文件可以照抄 |
| 16 | [[58]] | 工作大到一个会话装不下时，让一个只派活的协调代理管一群子代理；迁移时审查强度随结果递减 |
| 17 | [[60]] | 代码多到读不过来时：审查分七层、人工批准按改动风险定档、AI 审查三轮封顶，可以照着清单落地 |
| 18 | [[63]] | 让代理批量开维护 PR：删死代码、清过期实验、给 CI 提速，一处清理一个附证据的小 draft PR |
| 19 | [[67]] | 把代理接在团队已有的信号后面：工单标签触发分诊、PR 事件触发审查和自动修、告警经 API 开会话；Playbook 六要素（厂商自述） |
| 20 | [[64]] | PR 多到审不过来时把审查挪到计划：拷问、规格、对照真实代码核对、反方试图毙掉计划，再让代理在测试门内实现 |
| 21 | [[75]]，再看 [[81]] | 审查规则写进仓库并用三个 PR 测；副作用迁进 hook，开 PR 强制第二模型，审查回放跑两遍看方差 |
| 22 | [[79]] | 人不在电脑前也能推进：默认排队、插话只收窄范围、权限只批最窄一档，先 plan 再 goal |

**动手练习**：挑两个互不相关的小 issue，各开一个 worktree 让代理实现并开 PR，然后在一个 `/clear` 后的新会话里审查它们（[模式 P12](/patterns#p12)、[P13](/patterns#p13)）。

**延伸阅读**：[单代理推进与一人多线](/guide/solo) · [多代理协作与大任务拆分](/guide/multi) · [验收这一次的产出](/guide/review) · [评测代理本身与给动作把关](/guide/evals) · [接进 PR 与 CI](/guide/ci) · [云端与后台运行环境](/guide/cloud) · 用 Grok Build 的话见 [[34]]，用 Gemini CLI 做规划见 [[29]]

## 🧪 专家：长时自主任务与多代理 {#expert}

适合：想让代理连续跑几小时以上，或者设计多代理系统、评测体系。

| 步骤 | 读什么 | 读完能带走什么 |
|---|---|---|
| 1 | [[24]] | “上下文窗口就是数组”的心智模型；外层循环 vs 会话内循环 |
| 2 | [[17]] | 16 个代理、无编排者，靠 git + 锁文件 + Oracle 协作 |
| 3 | [[18]] → [[38]] | 扁平协作在数百代理时为什么失败；多代理 harness 每一版怎么改、为什么接受小错误率 |
| 4 | [[73]] → [[16]] | 先看最朴素的跨会话接力（功能清单全标未通过、进度文件、开工先跑基础测试），再看加了 Planner 和 Evaluator 的版本：做与查分离，以及模型升级后逐个拆脚手架 |
| 5 | [[19]]，再看 [[39]]、[[50]]、[[69]] 和 [[83]] | 怎么系统地评测代理：评分器、pass@k、接进生产、分数噪声、按轨迹打分；长程任务再加不给代理看的行为规格（[[83]]） |
| 6 | [[07]] 或 [[09]] | 团队级与产品级 harness 的内部机制 |
| 7 | [[30]]，再看 [[74]] | 互相依赖的大迁移怎么拆给并行代理：迁移分支、依赖图分批、临时脚手架；再看十个仓库的真实迁移里主代理怎么管依赖图、派活单六要素、worktree 不是沙箱 |
| 8 | [[35]] → [[36]] | 子代理和工具集怎么设计才省上下文：专长子代理 vs 用代码调用 MCP |
| 9 | [[45]]，再看 [[44]] 和 [[43]] | harness 会被替换时怎么设计系统；推理与编辑分给两个模型；在现成 harness 上做自己的客户端 |
| 10 | [[49]] | 代理把代码量放大一个数量级后，源代码管理和 CI 怎么重新设计；工程师的角色怎么变 |
| 11 | [[54]] → [[56]] | harness 怎么省 token（稳定前缀、工具按需加载）；怎么用两段式分类器代替人点批准，以及它漏掉了什么 |
| 12 | [[68]] | 把“做完了”交给程序跑的完成合约；计划切短会话、必要时再上无人值守 |
| 13 | [[59]] | 大任务上代理为什么提前收工；实现前由独立验证者建完成标准、实现者看不到用例，以及这样做的代价 |
| 14 | [[61]] | 单个代理连续跑 25 小时不跑偏：目标、里程碑、执行规则、状态日志四份 Markdown，原文可照抄 |
| 15 | [[62]] | 评测建好以后怎么爬分不自欺：先验证评分器，留出集、一次一个补丁、训练涨留出不涨就回滚 |
| 16 | [[71]] | 验证栈：推送前 critic 看轨迹，PR 上审查 skill + QA 真跑，再 iterate 到绿 |
| 17 | [[66]] | 11 个编码代理的源码解剖：七个子系统各自的最小和最大实现，两个“缺席”，以及自己搭外壳时的 18 条建议 |
| 18 | [[76]]，再看 [[80]] | 多代理团队值不值：工人放在瓶颈、强领队便宜工人；跑起来以后用 hook 挡缝合处事故（一文件一写者、检查移出可写路径） |

**动手练习**：把五种长时任务做法放在一起看：[长时自主任务专题](/guide/long-running)；再按 [[19]] 的路线图，为自己最常用的一类任务写 5 道评测题。
